# `src/services/db-ai-tools/`

## Map

- The AI chat's database tools — `db_query` (read-only), `open_query` (a Query tab holding a script the user runs) and `db_execute` (a change, once, after the user approves it with PPM's password) — on the saved connections with *Available to the AI chat* on, each tool on or off in Settings → Tools (`ai.ppm_tools`, all three on by default; `src/shared/ppm-tools.ts`). `db_query` names only the change tools that are on (`dbChangeHint`). `/api/db-tools-mcp` (`db-ai-tools-endpoint.ts`, mounted before auth) is built like `/api/tab-tools-mcp`: `mcp-http-endpoint.ts` + per-session tokens (`db-ai-tools-tokens.ts`). `db-ai-tools-tool.ts` holds the tool definitions and limits, `db-ai-connections.ts` which connections (light on purpose: `chat.service.ts` imports it, and the CLI loads `chat.service.ts`), `db-ai-target.ts` the adapter config with the *tool's* `readonly`, `db-ai-run.ts` the runs (`QueryScriptRun` for reads, `runApprovedScript` for one approved transaction), `db-ai-format.ts` rows as fenced untrusted data, `db-approval-broker.ts` the wait for the user's answer. Shared names and the approval's shape in `src/shared/db-ai-tools.ts`; the password check in `src/services/ppm-password.ts`. Chat side: `announceDbApproval` / `dbApprovalResolved` / `showWaitingDbApproval` in `src/server/ws/chat.ts`; the answer route `POST /api/db/ai-approvals/:requestId` in `src/server/routes/database.ts`. Browser: `src/web/components/chat/db-execute-approval-card.tsx`, `db-tool-card.tsx` + `src/web/lib/db-tool-call.ts`, `openAiQueryTab` in `src/web/lib/open-ai-tab.ts`, and the Query tab's *Run with write access (once)* (`write-once-dialog.tsx`, `writeOnce` on `/query/script`). Docs `docs/architecture/ai-chat-and-providers.md` → AI database tools; e2e `PPM_PLAYWRIGHT_MODULE=<playwright>/index.mjs node tests/e2e/ai-db-tools-e2e.mjs` (scripted provider in `tests/e2e/fixtures/db-tools-server.ts`; `PPM_DB_TOOLS_WEB_DIR` reuses a scratch build).

## Gotchas

- **A `db_execute` approval is answered over HTTP, never over the chat socket**: the card posts `{ approved, password }` to `/api/db/ai-approvals/:requestId` so a wrong password can be answered on the card while the approval stays pending, and so the password is never in a socket broadcast or the session trace. `ws/chat.ts` drops an `approval_response` naming one of these requests (`dbApprovalBroker.has`) — without that, an older bundle's generic Allow cleared the slot and took the card off every device while the broker went on waiting, so the AI sat out the ten minutes.
- **A session has one approval slot, and a provider's approval must keep it**: `entry.pendingApprovalEvent` is what `session_state` replays and what the browser's single `pendingApproval` shows. A `db_execute` announced while Claude or Codex waits on its own approval (parallel tool calls in a non-bypass session) used to overwrite it — the provider's card vanished and its turn waited forever. `announceDbApproval` now leaves the slot alone and returns true; `showWaitingDbApproval` shows the database approval once the provider's is answered. `tests/unit/ws/chat-db-approval.test.ts` pins it.
- **"PPM's password" is the auth token, so it proves presence, not a secret the AI lacks**: the token sits in `ppm.db`, which any process of the same OS user — the agent included — can read. The user chose it knowing that; the protection that holds regardless is that the connection's credentials never leave PPM and every change is shown, approved once and audited. Do not describe it as more than that.
- **`db_query` must open the connection read-only whatever the row says**: `aiTargetConfig(conn, db, true)`. `isReadOnlyQuery` is only the first layer; `SELECT nextval(...)` passes it and only a read-only session refuses it (the PostgreSQL test in `tests/integration/db-ai-tools.test.ts`). Likewise `db_execute` opens with `readonly: false` — the approval is what lifts a readonly connection, for that script only.
- **PPM owns the transaction a change runs in**: `db_execute` refuses `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVEPOINT` in the script before asking anyone, because a `COMMIT` inside it would keep half a change that the expected-rows check then could not roll back. MySQL and MariaDB still commit DDL implicitly; the tool description tells the AI.
