# `src/services/system-services/`

## Map

- `src/services/system-services/` is the Services page (`/api/system/services*`, routes in `src/server/routes/system-services.ts`): **two** `systemctl` spawns per scope — `list-units` plus one bulk `show` — never one per unit, with `journalctl -o json` behind the per-unit log. There is no D-Bus in Bun, which is why this shells out at all. Pass each unit as its own argv element after `--`: `-.mount` begins with a dash.
- The routes take a `ServiceBackend` (`service-backend.ts`): systemd on Linux, launchd on macOS — `launchd-collector.ts` (`launchctl print` of `system`, `gui/<uid>` and `user/<uid>`, each job printed and acted on in the one that holds it), `launchd-parse.ts`, `launchd-guard.ts` (PPM's own job by `XPC_SERVICE_NAME` and its ancestor pids, macOS's `com.apple.*` jobs, apps' per-launch `application.*` jobs, the root-only system domain), `launchd-logs.ts` (the job's own files, else `log show` from the job's start — the boot for a stopped one — newest hour first) and `launchd-job-index.ts` (the listing's pid → job map the tick walks by ppid, so per-job CPU/RAM costs no spawn).
- On macOS an app is an **application bundle**, not a cgroup: `apps-darwin.ts` walks each process's executable path (`process-path-darwin.ts`: the kernel's `proc_pidpath` unless it names a different file than `ps` printed) up to its bundle, reads `Info.plist` in-process (XML or binary, `plist-binary.ts`), and `app-icons-darwin.ts` turns the bundle's icon into a 64 px PNG with `sips`. The icon route still takes an app id, never a path.
- A pid names its Services row through `serviceKeyFromCgroup` in `system-services/app-cgroup-linux.ts`, which answers `"<scope>:<unit>"`. Three traps, all silent: the **innermost** unit wins (a user service nests under `user@1000.service`, so the outer one would put every desktop process on one row); living under `/user.slice/` does **not** make a unit a user one (`session-2.scope` and `user@1000.service` are both system units); and the scope is part of the key because `dbus-broker.service` exists in **both** scopes on an ordinary desktop. The Services page then sums the tick's own process rows in the browser (`services/service-resources.ts`) rather than recomputing rates in the services route, which has no counter state and would give one process two different figures on two pages of one window. A fourth trap lives on that side: a unit with no rows is only an em dash if it OUGHT to have processes, and neither `ActiveState` nor `SubState` answers that alone — systemd calls a mount `active (mounted)`, a finished oneshot `active (exited)` and a **listening socket `running`**, so going by the first dashed 97 of this host's 222 rows and going by the second still dashed 14. `resourcesFor` requires `SubState === "running"` **and** a `.service`/`.scope` unit, because a socket's processes live in the service it activates and its own `MainPID` is empty.

## Gotchas

- **launchd is not systemd, and most of the differences are silent**: `launchctl print gui/<uid>` is *a* listing of the user's jobs, not the listing: the background session's `user/<uid>` is the GUI domain's parent with jobs of its own (84 beside 450 here, none in both — an agent allowed in both sessions loads once, in the background one), and launchd answers for a label only in the domain that holds it (`Could not find service` from the other), so a job is printed and acted on in the domain it was listed from. Each listing carries its own `disabled services` section, and a disabled job is not bootstrapped — it appears **only** there. Launch Services adds an `application.<bundle id>.<n>.<n>` job for every launch of every app; those are the Apps page's rows, and leaving them out of the list does not stop a request naming one, so the guard refuses every action on them — stopping one quits its app, the terminal PPM was started from included. `(pe)`, an idle exit (memory reclaimed from an idle job — 155 of 446 jobs here), is not a failure, and neither is a job whose own `last exit reason` reads `JETSAM_REASON_MEMORY_IDLE_EXIT`; any other jetsam kill (`(jt)`, typically a job past its memory limit) is, the way systemd calls an OOM kill `failed`. Stop is `launchctl kill SIGTERM`, never `bootout`: a booted-out job leaves the list until the next login, and 13 of 24 third-party jobs here had no plist to load it back from. A KeepAlive job comes back by itself — 0.05 s after a kill for a job that had run a while, 8.2 s for one started 2 s earlier, because launchd will not relaunch within 10 s of the previous launch. A label's enable/disable override is kept **forever** and removing it needs root, so never click Enable/Disable on a throwaway job in a test. launchd sets `XPC_SERVICE_NAME` for a job's processes, and PPM inherits `XPC_SERVICE_NAME=com.hienlh.ppm` — which is how the guard recognises its own job. And there is no journal: a job's log is its own stdout/stderr files, else `log show`, whose cost is what it *prints*, not the window it is given — with a predicate naming one process, three days of a quiet daemon is 3 s, while runningboardd's 758k lines since boot are 32 s. So the reader asks for the last hour first and widens to the process's start (the boot, for a stopped job) only while the hour holds fewer lines than the box shows, inside one 10 s budget, one read at a time. A five-minute window — the first version — showed a line for 6 of 23 running jobs and 0 of 25 stopped ones, i.e. an empty box for nearly everything, failed jobs included. The pid predicate needs the process's start as its floor: pids wrap at 99,999, which this desktop reached in under three days, so a query by pid over the boot can answer with an earlier process's lines. Search by *message text* (`eventMessage CONTAINS`) is the one predicate never to use here: it decodes every message in the store, 105 s for one day.
