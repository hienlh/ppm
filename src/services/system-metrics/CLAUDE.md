# `src/services/system-metrics/`

## Map

- `src/services/system-metrics/` — Task Manager backend (`/api/system/resources*`): per-OS collectors, one long-lived PowerShell child on Windows (never spawn per tick — 32 MiB commit leak each), light/full SSE tiers with leases, guarded kill. UI in `src/web/components/system/` (floating window on desktop, tab on mobile)
  - Mission Center's pages are ported on top of it. Per-device collectors (`disk-devices-linux.ts`, `net-devices-linux.ts`, `gpu-devices-linux.ts`, `cpu-details-linux.ts`, `memory-linux.ts`, `fans-linux.ts`) feed the Performance page's device sidebar; the static labels beside them (DIMM vendors, disk models and serials, link speeds, driver/API versions) come from `hardware-inventory.ts` + `udev-db.ts` and are sent once, not per tick. Per-process GPU is DRM fdinfo (`gpu-fdinfo-linux.ts`). Signals are `signal-request-handler.ts` → `signal-executor.ts` behind the same parse → re-query → identity → guard sequence as the kill path, and `process-details-linux.ts` is the Details dialog.
  - macOS has a collector beside each Linux one, reading the kernel over `bun:ffi` where it can and one shared tool read a tick where it cannot (`darwin-tool-reads.ts` memoises each `ioreg`/`netstat`/`ifconfig` read for 1 s, so two collectors needing one spawn share it): `memory-darwin.ts` (Activity Monitor's figures from `host_statistics64`), `cpu-details-darwin.ts` (perf levels, the `pmgr` DVFS tables), `disk-devices-darwin.ts` + `disk-inventory-darwin.ts` (one `ioreg IOBlockStorageDevice` for every drive; partitions from `mount` + one `diskutil list -plist`), `net-devices-darwin.ts` + `wifi-darwin.ts` (CoreWLAN, never `system_profiler`), `gpu-darwin.ts` (one `ioreg IOAccelerator` for the GPU page and the per-process column), `process-io-darwin.ts` (`proc_pid_rusage`), `process-details-darwin.ts` (`ps`), and the sensors — `smc-darwin.ts`, `ioreport-darwin.ts`, `hid-temperature-darwin.ts`, taken once a tick by `sensors-darwin.ts` on top of `core-foundation-darwin.ts`. `device-collector-darwin.ts` assembles them into the tick.
  - **`os.cpus()` cannot express a core that is blocked on I/O**, and the failure is a *confident wrong number* rather than a gap: libuv's Linux `uv_cpu_info` reads the `iowait`, `softirq` and `steal` columns of `/proc/stat` into a throwaway, so a core parked in iowait reports a tiny total delta with no idle in it and `(total-idle)/total` comes out **100%** — one bar of the Overview per-core strip drew solid red, every tick, for a thread that was 3% busy behind a 191 MB/s write. `cpu-memory-collector.ts` samples `/proc/stat` itself (`parseProcStatCores`) and keeps `os.cpus()` as the off-Linux fallback; iowait is folded into not-busy the way `top` and Mission Center both have it, and softirq is counted as kernel time rather than dropped from the total. Do **not** also add `guest`/`guest_nice`: the kernel already counts them inside `user`/`nice`, so summing them deflates every percentage on a host running VMs. The whole-machine `total` hid this — one core's 6-jiffy window barely moves a sum over 24 — so verify per-core figures against `/proc/stat` directly, never against the total.
  - The contract everywhere here is **`undefined` = cannot measure**, and the UI renders that as an em dash. Never substitute `0`: "this GPU has no dedicated memory" and "this GPU has 0 MB of memory" are different claims, and `tests/unit/web/overview-gpu-card-vram.test.tsx` pins the difference.

## Gotchas

- **macOS has two "used memory" figures, and the one `top` prints is not Activity Monitor's**: `os.freemem()` on darwin counts only truly-free pages (66–124 MB on a 32 GB M1 Max), so `total − freemem` drew the Memory card at **99.7 %** while Activity Monitor said ~80 %. It survived because it agreed with `top` — `PhysMem: 31G used (3523M wired, 11G compressor), 75M unused` — and that agreement is the trap: `top`'s *used* counts the file cache, while Activity Monitor's **Memory Used** is App Memory + Wired + Compressed with **Cached Files** listed beside it (27.1 GB against `top`'s 31.9 on the same host at the same moment). Linux draws the same line (`MemAvailable`: cache the kernel can take back is not in use), so Activity Monitor's meaning is also the Linux one. `memory-darwin.ts` reads `host_statistics64(HOST_VM_INFO64)` over FFI (0.002 ms): used = (internal − purgeable) + wired + compressor, cached = external + purgeable, available = cached + free — **not** total − used, because 0.86 GiB of `hw.memsize` is held by the firmware in no page state and total − used would call it allocatable. Measured: 27.04 GiB against 27.01 from `vm_stat` run through Activity Monitor's formula. Two other corrections suggest themselves and both are wrong: `memory_pressure`'s "free %" (48–56 % on a machine using 27 of 32 GB) measures what could be reclaimed under duress, and `vm_stat`'s `inactive` mixes anonymous and file-backed pages, so neither is free RAM. Swap is `vm.swapusage` read as the `xsw_usage` struct — `node:os` carries no swap at all, and it rendered as an em dash on a Mac with 8 GB swapped. Compare against the platform's *headline* number, and make sure it is the right one of the platform's numbers, before fixing anything.
- **A platform gap parked as `null` becomes a *lie* the moment its caller has only one sentence for `null`**: the process Details reader was `/proc`-only and answered `null` everywhere else, and the route already spelled `null` as `PID <n> is no longer running` — true on Linux, where a vanished `/proc/<pid>` really is an exited process, and false on macOS, where it reported a renderer using 4.2% of the CPU as dead. A placeholder is only safe while nothing downstream *interprets* it, so give the unsupported case its own answer (`supportsProcessDetails()` → 501) before writing the `: null`. The gap itself was smaller than it looked: `ps` answers **ten of the eleven fields** on darwin (`process-details-darwin.ts`), two of them more directly than Linux — `lstart` is a real timestamp rather than jiffies to add to `btime`, and `user` is the login name already, so it works across users with no `/etc/passwd` lookup. Only `cgroup` has no equivalent. Three traps in the parse, all silent: macOS `ps` offers **no delimiter**, so fields are taken **positionally** — `lstart` is always five tokens (a single-digit day pads with two spaces, which a `\s+` split collapses rather than dropping) and `comm` must be **last**, since a path like `/Applications/Google Chrome.app/…/Google Chrome Helper (Renderer)` holds six spaces; `-M` may **not** be combined with `-o` (it prints the chosen columns *and* thread-layout leftovers on one line, which parses as nonsense instead of failing), so the thread count is a second call against the default format; and the state letters are **BSD's, not Linux's** — uninterruptible wait is `U` where Linux writes `D`, and `Z` is not an edge case (126 zombies against 645 sleepers on a normal desktop). Same family as the `Bun.spawn`-throws bullet above: reproduce a platform you do not have by taking its tools away, and verify the result against that platform's own output.
- **A CoreFoundation or Objective-C reference crossing `bun:ffi` must be a `u64`, never `T.ptr`**: macOS hands back short CFStrings and many object ids as **tagged pointers** — the value *is* the data, high bits set — and `CFStringCreateWithCString("CPU Stats")` answered `0xbc990da26c92796a`, above 2^53, while "Energy Model" got a heap address that crossed intact, which is why it works until it does not. `T.ptr` returns a JS double, so the reference is rounded on the way in, and handing it back (`CFRelease`, `CFStringGetCString`) dereferences a neighbouring address: the probe segfaulted at `0x10` with nothing reporting an error before it. Every ref in `core-foundation-darwin.ts` is a bigint (`T.u64` in both directions), `CFRelease(NULL)` is never called, and a string is read only after `CFGetTypeID` says it is one. CoreWLAN hit the same trap first (`wifi-darwin.ts` carries its object ids as u64 for this reason), which is the tell: any Apple API that returns an object can return a tagged one.
- **A Mac's sensors are three APIs, none needs root, and every read stops the event loop**: the SMC (temperatures, fans), IOReport (CPU/GPU energy and state residency → power and clock) and the HID event system (the SSD's "NAND CH0 temp") are all synchronous IOKit calls over `bun:ffi`, each with its own cost. An SMC read is a **firmware round trip** — 0.24 ms idle, up to 0.46 ms under load — so reading all 41 temperature keys was 11.5–19 ms of stopped event loop every tick. `smc-darwin.ts` reads the fans every tick and round-robins the rest inside a 4 ms budget (everything on the first call and after a 10 s gap), averaging each site over every sensor's *latest* value, because the sensors of one site read low/middle/high and a mean of only this tick's subset jumps; measured 4.1–4.7 ms a tick. IOReport's `IOReportCopyAllChannels` is 188 ms for 9341 channels **once** — copying per group costs 110 ms *per group* — and the array is then pruned to 13 channels; each tick is one sample and one delta, ~4 ms, and a gap over 10 s restarts the baseline instead of averaging over it. The NAND sensor costs 1.7 ms a read (33 ms to find) and moves over minutes, so it is read every 10 s. A worker thread cannot take any of this off the main thread: a release binary bundles only `src/index.ts`. Three attribution rules keep the figures honest: the SSD temperature goes only to the one `IOEmbeddedNVMeBlockDevice` (checked against `diskutil`'s SMART: 310 K = 37 °C, PPM 37 °C); GPU clock, power and temperature only where exactly one GPU is listed, since neither source names a GPU; and the first tick has no interval, so power and clock are absent on it, not zero. `PSTR` is whole-machine power and `F0Dc` is undocumented — neither is read.
- **Per-process GPU, disk and network on macOS come from three places, each with its own edge**: GPU time lives in the registry, not in a tool — every `AGXDeviceUserClient` child of the `IOAccelerator` names its process (`IOUserClientCreator` = "pid N, name") and carries `AppUsage[].accumulatedGPUTime` in **nanoseconds** (its `lastSubmittedTime` matched `CLOCK_UPTIME_RAW` to 0.01 s), so one `ioreg` read a tick serves the GPU page and the process column alike; a client absent from the previous read contributes nothing, or a window opened a moment ago reads as thousands of percent. Disk is `proc_pid_rusage(RUSAGE_INFO_V2)` (~3 µs a process), which answers **EPERM for another user's process** — an em dash, not 0, and the column is offered only when some pid answered. Network is `nettop`, which must run with **`-n`**: without it every sample resolves each connection's remote address (18 DNS queries a run, one run a tick while the page is open), telling the resolver what the machine talks to.
- **Wi-Fi on macOS: `system_profiler` scans, CoreWLAN does not, and the SSID is not PPM's to read**: `system_profiler SPAirPortDataType` looks like a query and is a **scan** — 3.8 s of wall time, and ping to the router went from max 73 ms to 135 ms while it ran, a network hitch on the machine being monitored. `CWWiFiClient.sharedWiFiClient().interface()` over the Objective-C runtime answers RSSI, noise, transmit rate, channel and band in 5–10 ms without scanning (`wifi-darwin.ts`: every id a u64, each message guarded by `class_respondsToSelector`, each read in its own autorelease pool). The SSID is nil without the Location permission, which a server process cannot obtain, so that row stays an em dash.
