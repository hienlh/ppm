# `src/services/chat-session-processes/`

## Map

- `session-slice.ts` (slice names, the CLI environment that routes a session), `session-shell-scripts.ts` (the two shell scripts, written to `<ppm dir>/bin/chat-session-shell/`), `leftover-decisions.ts` (what to stop, pure), `session-processes.service.ts` (probe, cgroupfs snapshot, `systemctl stop`, the one-minute sweep). Wired in at four places: `query` in `src/providers/claude-cli-process-group.ts` (the environment), `src/server/index.ts` (init after the providers, `stopCommandScopesSync` in `gracefulShutdown`), `src/server/ws/chat.ts` (`registerLeftoverSweeper`: what "busy" means), `chatService.deleteSession` (stop the whole slice). Setting `ai.leftover_processes_idle_minutes` (`src/shared/leftover-processes.ts`; unset = 30, 0 = off entirely, routing included). Tests: `tests/unit/services/chat-session-processes/`, `tests/integration/chat-session-processes.test.ts` (real systemd), `PPM_HOME=$(mktemp -d) bun tests/e2e/chat-session-processes-e2e.ts` (real CLI against a scripted fake API; `PPM_E2E_CLAUDE=<path>` picks another CLI)

## Gotchas

- **`CLAUDE_CODE_SHELL_PREFIX` gets the whole command line as ONE argument, and wraps stdio MCP servers too**: for a Bash call the CLI passes `prefix '<snapshot source> && … && eval <command> && pwd -P >| <file>'`, and for an MCP server `prefix '<command> <args…>'` (quoted). So the prefix must re-run `$1` in a shell — `run` does `"$shell" -c "$1"` — and must not add output of its own, because an MCP server's stdout is its JSON-RPC channel. The CLI also splits a prefix at its last `" -"` into program and flags, so a PPM dir whose path contains `" -"` cannot be routed at all (`withSessionSlice` leaves such a session untracked). A prefix the user set themselves wins and the session goes untracked.
- **`systemd-run --scope` execs in place, which is what makes the prefix invisible**: the pid the CLI holds, the exit code, the stdio and the process group stay the same, so the CLI's cwd tracking, `Exit code N` and the process-group cleanup in `claude-cli-process-group.ts` all behave as before. A `--unit=` / service (no `--scope`) would fork and break every one of those.
- **A `-` in a slice name is a level of the tree**: `app-ppmchat-<instance>-<session>.slice` lives at `app.slice/app-ppmchat.slice/app-ppmchat-<instance>.slice/…`, which is where `instanceDir` looks. The session id goes in with its dashes removed for the same reason, and `sessionIdOfSlice` puts them back. The instance is a hash of the database path because dev and prod share `~/.ppm`: one PPM must never judge the other's sessions idle.
- **"Attached" is decided by ancestry, not by cgroup**: a command running right now and a live CLI's MCP server sit in the same `ppmcmd-*.scope` cgroups as a leftover. What tells them apart is that some ancestor runs in PPM's own cgroup (the CLI); a process whose command returned was reparented to `systemd --user`. A sweep never stops an attached unit; deleting the session does.
- **The `systemd-run` shim puts an agent's own units into the session's slice — a deploy guard included**: anything the agent starts with `systemd-run --user` and no `--slice` is stopped once the chat is idle for the limit, and at once when it is deleted. A unit meant to outlive the chat (a guard that waits for PPM to go idle, a long benchmark) must pass `--slice=app.slice`. The shim and the prefix call the real `systemd-run` by absolute path; the shim stands first on the CLI's PATH, which the shell snapshot keeps.
- **Restart semantics are the old ones, on purpose**: commands used to live in `ppm.service` and die with it (`KillMode=mixed`); now they live outside it. So `gracefulShutdown` stops every `ppmcmd-*` scope and the startup pass stops those left by a server that died without one; units the agent made itself survive a restart, as they always did. The startup pass ignores "busy": it runs in the same tick routing is switched on, so nothing in a slice can be this server's yet.
- **`systemctl stop a b c` stops none of them when any one is gone**: systemd 262 answers "Failed to enqueue jobs: Unit … not loaded." (exit 5) whatever the order, and a command scope ending between the cgroupfs listing and the stop is ordinary. So `stopUnits` and `stopCommandScopesSync` stop everything in one call and, when that fails, one unit at a time, taking exit 5 as "gone already". The shutdown test raced on exactly this — `agentUnit()`'s own `systemd-run` scope is still being torn down — and was red or green per run; the two "…gone already" tests make it deterministic with a `ppmcmd-*.scope` directory made in cgroupfs that systemd has no unit for.
- **A fork's first CLI is untracked**: it resumes the source session under an id the CLI picks itself, so `chatSessionIdOf` returns nothing rather than filing its processes under the session it was forked from.
- **A running background Bash task keeps its session busy**: `hasBackgroundWork` counts `run_in_background` shells, so a dev server started that way holds back the sweep of everything else the session left until the shell stops or the session entry is cleaned up. It is attached to the live CLI anyway, so the sweep would not stop it itself.
