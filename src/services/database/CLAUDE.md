# `src/services/database/`

## Gotchas

- **SQLite has no `ILIKE`, and its `LIKE` ignores case for ASCII only**: a filter written with Postgres's `ILIKE` is a syntax error on SQLite. Case-insensitive matching goes through each dialect's `likeInsensitive` (`src/services/database/dialect-*.ts`): `ILIKE … ESCAPE E'\\'` on Postgres, plain `LIKE … ESCAPE '\'` on SQLite (already case-blind for ASCII; "Ä" and "ä" stay different because `bun:sqlite` loads no ICU), and `LIKE … ESCAPE CHAR(92)` under the column's own collation on MySQL, where a `_ci` collation ignores case and `LOWER(col)` would give up the index (the escape is named because a server whose `sql_mode` has `NO_BACKSLASH_ESCAPES` gives `LIKE` none, and as `CHAR(92)` because a backslash written as a string literal is spelled differently in each mode). Build filter SQL through the dialect, never by pasting an operator into a string.
- **A result read as objects loses the columns that share a name**: `SELECT 1 AS a, 2 AS b, 3 AS a` has three columns, but a row object holds one `a`, so a header built from `Object.keys(row)` shows two. bun:sqlite is worse than lossy: its `columnNames` is built from an object's keys too, so the repeat collapses *and moves* — `["b", "a"]` over three values, pairing every value with the wrong name. Read rows as arrays next to the driver's column metadata (postgres.js `.values()`, mysql2 `rowsAsArray: true`, bun:sqlite `.values()`), and for SQLite recover the names with `statementColumnNames` in `sqlite.service.ts`, which prepares the statement again as a subquery — never runs it — because SQLite then renames the repeats to `a:1`, `a:2`.
