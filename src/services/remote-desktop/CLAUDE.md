# `src/services/remote-desktop/`

## Map

- `src/services/remote-desktop/` — Remote Desktop: one ffmpeg per WS session (`remote-desktop-capture.ts` + per-platform `remote-desktop-capture-input.ts` + `remote-desktop-encoder-args.ts`) → Annex-B H.264 access units → WebCodecs; input via `remote-desktop-input.ts` facade over `remote-desktop-input-{win32,darwin,linux,uinput}.ts` (bun:ffi, no helper binary); host checklist in `remote-desktop-requirements.ts` (ffmpeg install command, macOS TCC pre-flight, Linux session/XTEST/uinput rows); display list in `remote-desktop-displays.ts` (`CGGetActiveDisplayList` order = avfoundation `Capture screen N`, names/bounds via one JXA call; X11 monitors via `XRRGetMonitors`). Linux specifics: `remote-desktop-linux-session.ts` decides X11 vs Wayland and resolves `DISPLAY`/`XAUTHORITY` (a Wayland session then takes a separate capture backend: `remote-desktop-portal.ts` holds the `org.freedesktop.portal.ScreenCast` session over libdbus FFI and `remote-desktop-capture-wayland.ts` runs `gst-launch-1.0` against the PipeWire node it hands back, producing the same Annex-B stdout ffmpeg does),  `remote-desktop-x11.ts` is the shared Xlib connection, `remote-desktop-evdev-key-map.ts` is the one key table both Linux backends use. Clipboard sync is `remote-desktop-clipboard.ts` (host side, one helper process per read/write) and `src/web/components/remote-desktop/remote-desktop-clipboard-client.ts` (which key combos mean copy/paste, plus the insecure-origin copy fallback). The in-session controls are `remote-desktop-toolbar.tsx` (desktop, RustDesk's grouped menus) and `remote-desktop-mobile-toolbar.tsx` + `remote-desktop-mobile-settings.tsx` (thumb zone), with the scale maths in `remote-desktop-view-style.ts`. Host audio is `remote-desktop-audio.ts` (a second ffmpeg, Opus in Ogg) demuxed by `remote-desktop-ogg-opus.ts` and played by `use-opus-audio-player.ts`; privacy mode is `remote-desktop-privacy.ts` (X grabs + DPMS); host resolution is `remote-desktop-resolution.ts` (XRandR FFI) with the menu collapse and the fit-local decision in `remote-desktop-resolution-list.ts`; the custom image-quality maths ported from RustDesk's `video_qos.rs` are `src/shared/remote-desktop-custom-quality.ts` behind `remote-desktop-custom-quality-dialog.tsx`; screenshot/recording are `remote-desktop-recording.ts` + `use-remote-desktop-recorder.ts` (client-side `MediaRecorder` over the canvas). The WebRTC transport is an optional downloaded relay: `mediamtx-catalog.ts` (pinned version + SHA-256 per platform), `mediamtx-install.service.ts`, `mediamtx-paths.ts`, `mediamtx-config.ts` (the generated config — the one place the relay's exposure is decided) and `mediamtx-process.ts` (one relay per session, free ports, waits until it is really listening); `buildCaptureArgs`'s last argument swaps `pipe:1` for an RTSP push, `remote-desktop-whep-registry.ts` + `POST /api/remote-desktop/whep/:ticket` are the authenticated, **ticket-addressed** handshake proxy, and `use-webrtc-canvas-video.ts` paints the track into the same canvas the WebCodecs path draws to. Settings pane `settings/remote-desktop-settings-section.tsx`. Codec choice comes from `workingEncoders()` in `media-transcode/ffmpeg-capabilities.ts`, which probes *every* candidate rather than short-circuiting. Routes `src/server/routes/remote-desktop.ts`, WS `src/server/ws/remote-desktop.ts`, UI `src/web/components/remote-desktop/`, e2e `tests/e2e/remote-desktop-e2e.mjs`

## Gotchas

- **Remote desktop on macOS (avfoundation)**: address the screen by **name** (`-i "Capture screen 0"`), never by index — the device list reorders at runtime when a Continuity Camera joins (index 3 became the iPhone). `-framerate` is ignored (the screen input delivers at display refresh, 120–165 fps, with a stuck pts) → `-use_wallclock_as_timestamps 1` + `-vf fps=30`. ffmpeg-avfoundation ignores SIGTERM/SIGINT → `proc.kill("SIGKILL")` or it leaks one process per session. No Screen Recording grant = **black frames, no error**; no Accessibility grant = silent no-op input — both are pre-flighted in `remote-desktop-requirements.ts`, never inferred from failures. TCC keys the grant to the `bun` executable.
- **Remote desktop text injection on macOS**: `CGEventKeyboardSetUnicodeString` still carries a keycode, and IMEs that hook by key (OpenKey/EVKey) re-read keycode 0 as a literal "a" (`"日本"` → `"â"`); function/unassigned keycodes produce no text at all. The carrier is Space (`TEXT_CARRIER_KEYCODE`). Text is still subject to the host's active IME (Telex rewrote "World" → "ửold") on every OS.
- **Remote desktop on Linux is chosen per *session*, not per platform, and Wayland must win the tie**: `process.platform === "linux"` says nothing about how to capture or inject. A Wayland session almost always also runs XWayland, which sets `DISPLAY` and answers `x11grab` **successfully** — with a view of XWayland clients only, i.e. a black or half-empty screen rather than an error. So `remote-desktop-linux-session.ts` checks Wayland *before* X11, and `XDG_SESSION_TYPE` outranks both. It also has to *probe* rather than read the env: a PPM started by its systemd user unit has no `DISPLAY`/`XAUTHORITY` at all while a full desktop runs two feet away, so the fallbacks are the `X<N>` socket in `/tmp/.X11-unix`, the `wayland-N` socket in `$XDG_RUNTIME_DIR`, and for auth the `xauth_*` file Xorg was launched with (`-auth /run/user/1000/xauth_XXXXXX`) before `~/.Xauthority`. ffmpeg is then spawned with that env merged over `process.env`. Wayland capture goes through a **different backend entirely** (`remote-desktop-capture-wayland.ts`) rather than another ffmpeg grabber — see the portal bullet below.
- **Key injection on Linux goes through evdev codes, never keysyms**: `XKeysymToKeycode(XK_a)` answers "which key currently *produces* an a", which on an AZERTY host is the physical Q key — so a keysym table silently transposes the whole keyboard for anyone not on a US layout. `remote-desktop-evdev-key-map.ts` maps `KeyboardEvent.code` → evdev code, which names the physical switch just as `code` does; X11 keycode = evdev + 8 (`X11_KEYCODE_OFFSET`), verified against a live server for all 50 spot-checked keys. The same table feeds uinput, which wants the raw code. X11 also has no "type this string" call: `text()` uses the real keymap when the character is in it (all ASCII, no round trip) and otherwise borrows a keycode with no keysyms, binds it to `0x01000000|codepoint`, and needs a real ~12ms delay after the remap — the server applies it at once but the focused *client* only learns from its `MappingNotify`, so a key pressed sooner is read with the old mapping.
- **Wayland capture is a portal session that must outlive the capture, and the three things that make it work were each measured**: a compositor shares the screen only through `org.freedesktop.portal.ScreenCast`, which is D-Bus, which Bun does not speak — so `remote-desktop-portal.ts` is `bun:ffi` against `libdbus-1.so.3` (present on any host with a session bus). Three findings turn this from impossible to routine. **`OpenPipeWireRemote` is never called**: the documented flow ends by receiving a PipeWire *file descriptor*, which no shell-out (`busctl`, `gdbus`) can hand to a separate process — and it turns out not to be needed, because the node lives in the user's own PipeWire daemon, so a bare `pipewiresrc path=<node>` reaches it through `$XDG_RUNTIME_DIR/pipewire-0` (measured: negotiated `BGRA 1920x1080` with no fd in the pipeline). **The D-Bus connection owns the session** — the node dies with it, so the handle is held for the capture's whole life and `dbus_bus_get_private` is used rather than the shared connection, which is refcounted process-wide. And **`persist_mode: 2` + a stored `restore_token`** (under `getPpmDir()`, 0600) is what stops a consent dialog appearing on the *host's* screen every session, which on a remote desktop is a prompt only someone sitting at the machine could answer; the first session still asks. ffmpeg is not the capture tool here at all: reading PipeWire needs `--enable-libpipewire`, which distributions do not do (Arch's own `ffmpeg 2:9.0.1-4.1` does not), so GStreamer does it — exactly as RustDesk does (`Depends On: gst-plugins-base gst-plugin-pipewire` + `libdbus-1.so.3` linked in; it is Rust, not magic). Four traps in the pipeline, each silent. **`videorate max-rate=30` does not cap** — measured 59 fps through it, and 133 fps at `max-rate=60`; only a capsfilter `video/x-raw,framerate=30/1` caps. That same capsfilter is also **what makes an idle desktop watchable**: a portal stream is damage-driven and a still screen pushed **14 frames in 60 seconds**, so a viewer joining a quiet host would see nothing at all — `videorate` duplicates the last frame and held **29.6 fps on a completely static screen**, which keeps keyframes flowing so a late joiner syncs within one GOP. **`vapostproc` + `video/x-raw(memory:VAMemory)` must pair with `vah264enc`** and not with `x264enc`, or every frame is downloaded back out of VA memory; the GPU path cost **14.9% of a core at 1080p30 against 52% for software conversion uncapped**. And the **portal stream dies under consumer churn** — it wants one long-lived `pipewiresrc`, so anything that reconnects per quality change must re-run the handshake rather than reattach. Measured end to end through `startCapture`: first access unit at **430 ms**, 28.8 fps, 3.2 Mbit/s, SPS parsed from GStreamer's bytes by the same `AccessUnitAssembler` ffmpeg's output feeds. `listDisplays()` still answers `[]` on Wayland and that is correct — the portal's own dialog chooses which output is shared, so PPM neither enumerates nor picks.
- **Xlib's default I/O error handler calls `exit()` on the PPM server**: a logout, a GPU reset or `systemctl restart sddm` makes libX11 print `XIO: fatal IO error` and terminate the *calling process* — every project, terminal and chat session gone because someone logged out of the desktop. `remote-desktop-x11.ts` replaces all three handlers (`XSetErrorHandler`, `XSetIOErrorHandler`, and libX11 ≥ 1.7's `XSetIOErrorExitHandler`, which cancels the exit that happens even when the first one returns) and holds the `JSCallback`s in module scope — a GC'd callback leaves Xlib calling a freed trampoline, i.e. a segfault instead of the crash it was installed to prevent. A connection that took an I/O error has no safe call left on it, not even `XCloseDisplay`, so it is dropped un-closed and the next caller reopens.
- **`xrandr` the binary and `libXrandr` the library are different packages**: this dev host has `libXrandr.so.2` and no `xrandr`, so anything that shells out to enumerate monitors reports "no displays" on a working desktop. `remote-desktop-displays.ts` reads `XRRGetMonitors` over FFI (`sizeof(XRRMonitorInfo)` = 56 on x86-64: name Atom at 0, primary at 8, x/y/w/h at 20/24/28/32) and falls back to one whole-root-window entry when the library is absent. X11 puts every monitor in one root coordinate space, so a per-monitor capture is a crop — `-video_size WxH -i :0.0+X,Y` — and `-i :0.0` alone grabs the union of all of them.
- **A uinput injector needs two devices, not one**: libinput classifies a device from the capabilities it declares, and one device advertising both a full keyboard and absolute axes is typically read as a *touchpad* — which then applies pointer acceleration and treats absolute coordinates as relative motion, so the pointer drifts instead of landing. `remote-desktop-input-uinput.ts` creates a pointer device (absolute axes + buttons + wheel + `INPUT_PROP_DIRECT`) and a keyboard device separately, declares every key it will ever send (`UI_SET_KEYBIT`; an undeclared key is dropped by the kernel silently), and `UI_DEV_DESTROY`s both on exit or they pile up in the compositor's device list on every restart. Derive the ioctl numbers from real headers — `_IOW` encodes the struct size, so a wrong `sizeof` yields a different request number and `ioctl` fails with `EINVAL` for no visible reason. uinput carries key *codes*, so there is no `text()` at all: a phone soft keyboard that reports no key codes cannot type on a Wayland host.
- **VAAPI is the only hardware H.264 an AMD Linux host has, and its args are position-sensitive**: `h264_amf` is Windows-only and `h264_qsv` is Intel-only, so before `h264_vaapi` was added to the candidate list every Radeon machine fell all the way back to software libx264. It is not a drop-in `-c:v` swap: `-vaapi_device` has to precede `-i` (it opens during input setup) and the frames must be uploaded in the *same* `-vf` chain (`format=nv12,hwupload`) — a second `-vf` replaces the first rather than combining — while `-pix_fmt yuv420p` has to be dropped, because a software pixel format on the output makes ffmpeg reject the hardware frame context. The capability probe test-encodes for real (`encoderWorks`), which is what stops `h264_nvenc` being chosen on this Intel-only host purely because the build lists it.
- **Owning a clipboard is not a one-shot call, which is why the host side shells out**: an X11 clipboard owner has to stay alive answering `SelectionRequest` events for as long as it holds the selection, so there is no "set the clipboard" Xlib call to FFI — `xclip`/`wl-copy` already fork a helper that does exactly that, and `remote-desktop-clipboard.ts` spawns them with `DISPLAY`/`XAUTHORITY` merged in (same as ffmpeg, since a systemd-started PPM has neither). The cost is a package the host may not have, and that is not hypothetical: this dev machine had **none** of xclip/xsel/wl-copy while running a perfectly good X11 desktop — the same trap as `xrandr` the binary vs `libXrandr`. So a missing tool is reported as `clipboard.available === false` carrying an install command, never as a silent no-op, and a paste still lands by *typing* the text as a fallback. It cannot be a `requirements` row though: that checklist only renders while video or input is unmet, so a clipboard row would be invisible on exactly the working hosts that are missing the tool — hence a separate `clipboard` field on the readiness response. Two more. On a **Wayland** session a working `xclip` is *worse* than none, because it addresses XWayland's own clipboard rather than the one the user sees, so the X pair is never even considered there. And the two directions feed each other unless the last synced text is remembered (client pastes T → host clipboard becomes T → the next read pushes T back → the client's own write re-arms it), which is what `lastClipboardText` is for. Windows goes through PowerShell with base64 on **both** sides, because `Get-Clipboard`/`Set-Clipboard` cross stdout/stdin in whatever console code page is active; `-Raw` plus a `$null` guard are needed too, or a multi-line clipboard arrives as an array of lines and an empty one makes `GetBytes` throw.
- **Reacting to a backpressure *spike* is what makes remote desktop stutter, and the higher-resolution rung is the smoother one**: both findings are counter-intuitive and both were measured on a 3440x1440 host. First, discarding one delta access unit makes every later delta in that GOP undecodable, so the client freezes until the next keyframe — which means a **120 ms** buffer spike bought a **502 ms** frozen picture, and a spike that short is a client GC pause or one wifi retransmit that would have drained by itself. `congestionState` therefore requires the socket to stay over threshold for `BACKPRESSURE_SUSTAIN_MS` before anything is dropped (same spike after: **20 ms**), and only sustained congestion feeds the adaptive ladder, because degrading a rung respawns ffmpeg for ~400 ms — a worse hitch than the one it was avoiding. The GOP is the other half of the same lever: it bounds every resync freeze, and halving it to half a second costs **no bitrate at all** (-0.0% at `balanced`, -0.1% at `high`, +0.3% at `tiny` against a full-motion source) because the encode is rate-capped, so extra keyframes redistribute the same budget rather than adding to it. Second, and the reason a "safe" default can read as lag: **1440p60 measured `gap p50=16.6 p95=22.7 max=30 ms` while 720p30 managed only `p50=33.3 p95=41.4 max=49 ms`** — the frame interval is half as long, so the same absolute jitter is a smaller fraction of it, and the expensive rung is the *smoother* one. A 30 fps ceiling cannot be fixed by sharpening the frames. Two traps that follow: a preset's `height` has to be a **ceiling** (`scale=-2:'min(ih,H)'`), or a 1440p rung on a 1080p host upscales and spends the whole rung's bitrate on interpolated pixels; and `auto` deliberately still stops at `balanced` (rising unprompted to 16 Mbit/s would manufacture congestion and spend a metered user's data), so the top rungs are reachable only by pinning them — the picker is the feature, not a fallback, and the pin is remembered with `persistDevicePref` (localStorage only, like `lspEnabled`) because the server round-trip would let a LAN desktop pin 1440p60 for a phone on mobile data. What comes back out of localStorage is untrusted the same way a rung off the wire is, hence `parseQualityChoice` rather than a cast — it lives in the shared ladder and not in the store because importing the store reads `localStorage` at module scope and throws under `bun:test`. Finally, the things that are **not** the bottleneck, so nobody re-measures them: QSV's `async_depth` (no effect — one AU per frame at cadence either way), x11grab at 3440x1440 with *software* swscale (holds both 30 and 60 fps on an i9-12900K), and moving the downscale onto the GPU with `scale_vaapi` (no latency win, marginally worse p95). The client is not either: `use-h264-canvas-decoder.ts` configures `optimizeForLatency` and draws straight from the `output` callback with no queue.
- **An exclusive device grab is already taken, so blocking the host's input is an X grab and not evdev**: privacy mode's obvious implementation is `EVIOCGRAB` on every `/dev/input/event*` — and on this machine it returned **EBUSY on 3 of 4 devices** (`errno=16`, both keyboards and the wireless receiver; walking `/proc/*/fd` named the holder: **toshy**, a keyboard remapper, alongside Xorg). The grab is exclusive, so anything already holding it — toshy, kmonad, keyd, xremap — wins, and the first design would have reported "privacy mode on" while the local keyboard kept typing. Worse, the support probe only tested `devices[0]`, which happened to be the one device that *was* grabbable, so it answered "available" for a feature that could not work. The implementation is `XGrabKeyboard` + `XGrabPointer` with `owner_events=False`, plus **`XTestGrabControl(dpy, True)`** — that last call is the whole trick, because it makes a client's own XTEST events impervious to its own grab, so the remote session keeps injecting while the local user is locked out. Both grabs or neither: one of the two succeeding leaves the host half-controllable. Blanking is **DPMS**, which lives in **libXext**, not libX11 (`DPMSForceLevel(dpy, 3)`); it blanks the *output* and leaves the framebuffer, which is why x11grab keeps streaming a screen nobody local can see — and it needs re-asserting on a timer, because the injected XTEST events reset the idle timer that would otherwise hold it off. Probe DPMS for real (`DPMSQueryExtension` *and* `DPMSCapable`) rather than assuming the extension implies a capable output. Verify a grab from a *second* X connection (`XGrabKeyboard` there returns 1 = AlreadyGrabbed while it holds) — the process holding it cannot observe its own exclusivity.
- **The Ogg muxer buffers a whole second per page, which reads as audio latency and not as a setting**: host audio arrived ~2000 ms late, and none of the usual suspects were it — not the encoder (`libopus -application lowdelay -frame_duration 20`), not the socket, not the decoder. `-page_duration`'s default is **1 second**, so ffmpeg held ~50 Opus packets before emitting anything; `-page_duration 20000` (+ `-flush_packets 1`) took it to ~40 ms. It was found by *measuring page arrival times*, because every layer above and below looked correctly configured. Two more measured details that stop a re-investigation: a silent PulseAudio sink still produces packets (**3 bytes** each, against ~285 with real sound), so "packets are flowing" is not evidence of audio; and the demuxer's `concat` must **always copy** — returning a `subarray` view for the single-part case both pins the whole received chunk alive and hands out a packet pointing into a buffer that is about to be replaced. Detect pulse from `ffmpeg -demuxers` with a pattern that tolerates its real column layout (` D  d  pulse`): `/^\s*D\s+pulse\b/` requires whitespace immediately after the `D` and rejects every working build.
- **Changing the host's own resolution is a *sequence* of X calls, and the wrong order leaves a desktop with a dead strip**: the root window is a container for the CRTCs and neither may be outside the other, so any dimension that grows needs `XRRSetScreenSize` **before** `XRRSetCrtcConfig` (a CRTC past the screen bounds is refused) and trimming it down has to come **after** (a screen smaller than a live CRTC is equally invalid). A switch where one dimension grows and the other shrinks — 1920x1200 → 2560x1080 — needs both, which is why the decision is the pure `planResolutionSwitch` with its own test rather than an `if (growing)` pair: get it wrong and the mode applies, the root window keeps the wrong size, and nothing errors. Three more traps. The struct offsets are written out because a wrong one does not fail, it reads a neighbouring field and returns a plausible-looking mode list — check the read path against the kernel's own `modes` file under `/sys/class/drm/<card>-<connector>` (37 modes over XRandR vs 43 there on this host: X drops the interlaced/NTSC duplicates, and all 15 distinct sizes match). `XRROutputInfo.npreferred` is a **count** of preferred modes at the head of the list, not an index, so reading it as one marks the wrong mode native. And the menu must collapse to one row per *size* (37 timings → 15 rows), where the surviving mode has to be the **live** one when the host is on it — keeping the highest refresh instead leaves a host on 3440x1440@60 with nothing ticked while it also advertises @100. Restoring the original mode on teardown is not optional: this is the one session setting that outlives the session on the host's own screen. `-video_size` is fixed at spawn, so a switch is also a capture respawn.
- **RustDesk's "image quality" is bitrate and frame rate only — never resolution — and its Custom percentage is not a percentage of anything**: the menu is exactly four radio items (`toolbarImageQuality` in `flutter/lib/common/widgets/toolbar.dart`) — Good image quality, Balanced, Optimize reaction time, Custom — with no `auto` and no resolution, and `Quality` in `codec.rs` is the matching enum. PPM first shipped five rungs that *downscaled* beside a separate resolution menu, which is one menu too many and cost real picture quality: on a 3440x1440 host `balanced` streamed 720p, and measured, that downscale bought **1.17 Mbit/s against 1.26 Mbit/s** for native at the same cap — 7% of the bandwidth in exchange for 4.8x the pixels, because a desktop is mostly static and H.264 spends bits on *change* rather than on area. Neither came close to its cap, so it was pure loss. Dropping the scale filter also retires the upscale hazard it was guarding against, since nothing scales at all. The flicker that prompted this is worth recording precisely, because the plausible diagnosis was wrong: the old top rung asked for a flat 25 Mbit/s at 1440p60, and over a link that cannot carry that the capture pipe backs up and **ffmpeg throttles itself** — 22.9 of 60 fps arriving with gaps to **181 ms** over 4 Mbit/s, bursts and stalls that read as continuous flicker at that resolution, where the same rung on an unthrottled link held 60.0 fps at `p50=16.5ms`. It was *not* the frame-dropping path: `congestionState` never fired, because **`ws.getBufferedAmount()` is Bun's userspace queue and drains into the kernel socket buffer**, so it never reaches the 512 KB threshold — not even at 0.4 Mbit/s behind a relay applying real TCP backpressure. The keyframe rate is the tell (0.75/s against a 30-frame GOP is ffmpeg encoding at 22 fps, not a server discarding two thirds of its output), and the consequence is that the whole backpressure ladder hangs off a signal that is effectively inert on this host — anything built on it is unit-tested at best. With ratios instead, the top rung is `base_bitrate(3440,1440) x 1.5` = 6 Mbit/s and holds **30.0 fps with a 42 ms maximum gap over both a 5 Mbit/s and a 2 Mbit/s link**. A chosen rung is a **ceiling**, never a freeze (`video_qos.rs`: "user set image quality => update to the maximum ratio of the latest quality"), which is what the old `autoQuality = false` got backwards. `video_qos.rs` turns the slider into a *ratio* as `(percent * 2) / 100` clamped to 0.2–40.0, so the dialog's default **50% is ratio 1.0** and 100% is **double** the base rate; the named rungs are the same ratio under another name (BR_BEST 1.5, BR_BALANCED 0.67, BR_SPEED 0.5). What it multiplies is a **nearest-pixel-count lookup**, not a formula — a 13-row table from 640x480@400 kbps to 7680x4320@12000 kbps, scaled by the ratio of the real pixel count to the matched row's, giving `base_bitrate(3440,1440) = 4000` kbps. Three traps in the port, all in `src/shared/remote-desktop-custom-quality.ts`: the smallest row makes `baseBitrateKbps(0, 0)` round to **0** and ffmpeg refuses a zero bitrate, so it needs a floor; the custom rung has to keep the *display's own* height or it silently re-introduces the downscale the menu is not supposed to have (`effectivePreset()` overrides `fps` and `bitrate` and nothing else); and leaving custom for a named rung whose id is the one already in force must force a respawn, because `applyPreset` early-returns on an unchanged id and ffmpeg keeps running the custom numbers while the menu ticks a preset — verified over the real WS, not reasoned about. The **More** checkbox raises the ceiling from 100% to 2000%, so it decides what the percent is clamped to and has to be read out of storage *first*, and unticking it must re-clamp and re-commit or the host keeps encoding at a rate the dialog no longer shows. Ours debounces each commit by 400 ms because a bitrate change respawns ffmpeg here; RustDesk retunes its encoder in place and needs no such delay. "Optimize reaction time" is deliberately **not** copied onto a low rung: in this ladder the high rungs are the low-latency ones (see the backpressure entry above).
- **Virtual display cannot be done from userspace, so PPM does not pretend to offer it**: RustDesk's "virtual display" is a **signed IddCx driver** it ships and installs on Windows; on Linux the equivalent is `xf86-video-dummy` configured into `xorg.conf` and loaded *at X startup*, which no running process can add to a live server. There is no FFI call, no extension and no ffmpeg flag that creates a head — `XRRSetScreenSize` can resize the framebuffer past the panel but the CRTC still drives the one real output, so the extra area is never scanned out and is not a second display. The feature is therefore absent rather than stubbed; a menu item that silently does nothing is worse than no menu item.
- **WebCodecs is secure-context only, so Remote Desktop and the Android viewer cannot show a picture on a plain-HTTP LAN address** — which is how a phone or tablet normally reaches PPM. Measured in one browser at one moment: `VideoDecoder` is `undefined` on `http://192.168.98.96:3210` and present on `http://127.0.0.1:3210`, while `RTCPeerConnection` exists on both. Nothing warns; the viewer just reports "this browser has no WebCodecs" about a browser that is fine, which is why `missingDecoderReason()` branches on `window.isSecureContext` instead. The way out is WebRTC, and in Bun that means a **downloaded binary**: there is no WebRTC stack in the runtime, GStreamer's `webrtcbin` **segfaults PyGObject** on GStreamer 1.28.7 + Python 3.14 (`gst_webrtc_session_description_copy` → `gst_sdp_message_copy` → `g_strdup` on a malformed emails array — it dies just *reading* the offer, and rebuilding the description from SDP text does not help) *and* would put GStreamer + PyGObject on every Windows and macOS host, and `@roamhq/wrtc` only accepts raw i420, i.e. it would discard the hardware H.264 encode and re-encode in software. `mediamtx-*.ts` is the answer: MediaMTX repackages the H.264 ffmpeg already produced (verified — 1920x1080 Main@4.0 in, `video/H264` at the same size out) for 0.6% of a core and 55 MB RSS. Four traps in wiring it. Its **shipped `mediamtx.yml` must never be used**: it listens on every interface with RTMP/HLS/SRT/MoQ/API/metrics/pprof on, and MoQ writes `auto.crt`/`auto.key` beside itself on first start — PPM generates its own config and every switch is spelled out, because MediaMTX *rejects unknown keys* (`json: unknown field`), so a renamed key fails loudly instead of silently leaving a listener open. The **ICE/UDP port cannot be loopback** — WebRTC media is peer-to-peer, so confining it breaks every remote viewer while the page still connects; what protects it is the per-session ICE ufrag/password, which is why a test asserts the port is *not* loopback. `filesrc` **cannot read a FIFO** (it probes for seekability and closes it, so ffmpeg takes EPIPE) — open the FIFO yourself and hand over `fdsrc fd=N`. And the relay answers **404 until the publisher's first packet**, which a quality change re-creates by respawning ffmpeg, so the browser's WHEP handshake must retry rather than fail. Peer-to-peer also means a viewer on the **Cloudflare tunnel** has no route for the media at all: the handshake is proxied over HTTPS and succeeds, then nothing arrives, and Chromium takes **15 s** (measured, no candidate reachable) to call the connection `failed`. So `use-webrtc-canvas-video.ts` gives ICE `CONNECT_DEADLINE_MS` and the connection hook reconnects asking for the WebSocket stream, remembered for the tab in `sessionStorage` — but only where WebCodecs exists: behind the tunnel's HTTPS it does in any browser that ships it, on a plain-HTTP LAN origin it never does, and there the WebRTC error stands. Last: `startCapture` keeps `stdout: "pipe"` in both modes even though nothing reads it when publishing — making it conditional widens Bun's spawn type so `proc.stdout` is possibly-undefined everywhere below, the same family as the `ReturnType<typeof Bun.spawn>` trap above.
