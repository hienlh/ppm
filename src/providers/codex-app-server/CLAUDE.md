# `src/providers/codex-app-server/`

## Gotchas

- **Codex runs one turn per thread and swallows the second**: a `turn/start` issued while a turn is running does not error — it resolves with the **already-running** turn (same id, `status: "inProgress"`) and discards the new input, so a mid-turn follow-up vanished with nothing to log. `turn/interrupt` is the only way to cut a turn short, and it needs `{threadId, turnId}` (`threadId` alone is rejected); the turn id comes from the `turn/started` notification. A mid-turn follow-up goes in with **`turn/steer`** instead (`{threadId, expectedTurnId, input}`, codex ≥ 0.157): the model reads it at its next step boundary — after the current tool call or message, not after the whole task — and codex emits it as a `userMessage` item in the same turn. Only what cannot be steered (`later`, `now`, an unnamed turn, a compaction, a refused steer) waits in `pendingTurns` for `turn/completed`, which is also what an interrupted turn reports. Before steering existed every follow-up was queued, so a message typed mid-task sat unread until the task ended.
- **A signed-out Codex account fails slowly, and its retry notices are not errors**: a revoked or expired ChatGPT login does not fail `initialize` or `thread/start` — codex opens the turn, then sends `error` notifications with **`willRetry: true`** ("Reconnecting... N/5", ten of them over ~24s) before a final `willRetry: false`. The cause is only in `error.additionalDetails` (`workspace routing discovery unauthorized (401)`), never the headline. Mapping every `error` to a fatal event made the proxy give up at the first reconnect, and a retrying client then kept a dozen app-servers starting at once until the server stopped answering its health check. `codex-event-mapper.ts` turns retry notices into `status_update`; `codex-auth-failure.ts` recognises the 401 on the first one; `codex-account-auth-state.ts` benches the account (hard exclusion, unlike a quota park) so the turn rotates or fails in milliseconds; and `proxy-agent-turn.ts` caps concurrent proxy turns with a 429. Selection also has to ignore the usage figure for such an account: the usage endpoint keeps serving its last good reading, which made a dead account look emptier than a working one.
- **A codex subagent is a session file of its own**: codex writes every spawned agent as a full rollout in the same `$CODEX_HOME/sessions` tree, with the same `cwd` as the conversation that spawned it — so a cwd filter alone lists each spawn as a top-level session that opens mid-stream, because a subagent's task is handed over as encrypted scaffolding and never appears as a `UserMessage` in its own transcript. `session_meta.parent_thread_id` is what tells the two apart. The parent names each spawn twice (`SubAgentActivity` `started`/`completed`) under **different item ids** but one `agent_thread_id`, which is why `codex-subagent-thread.ts` keys the card on the thread; `codex-history.ts` then reads the child rollout and hangs it under that Agent card.
- **A child Codex rollout writes two `session_meta` records, and only the first describes the file**: a spawned subagent's rollout carries its own header first and its parent's (forked context) second — reading the second as authoritative would misread the file's own `cli_version`/format. `readRolloutHeader` (`codex-rollout-header.ts`) and the live tail parser (`codex-rollout-tail-parser.ts`) both ignore every `session_meta` after the first.
- **A streaming rollout parser cannot use whole-file look-ahead**: it commits to legacy vs `item_completed` format from the *first* `session_meta`'s `cli_version` (`item_completed` shipped in codex cli 0.154.0) and never revisits that choice mid-file — there is no later point at which re-reading the whole file to check is acceptable for a live tail. A `compacted` or `thread_rolled_back` record rewrites the file's *content*, not its format, so `codex-rollout-tail-parser.ts` resets its de-dupe state on those but keeps the format decision from the header.
- **Codex's `FileUpdateChange.diff` is a diff only for an update**: for `add` and `delete` it is the file's **raw content**, and an update may end in `\n\nMoved to: <path>`. Parsing all three as a unified diff (`diffToOldNew`) dropped every line without a `+`/`-`/space prefix, so a created file counted +0. The rollout's `item_completed` FileChange carries `changes` as a dict keyed by path, not the live array (`rolloutFileChanges` vs `fileUpdateChanges` in `codex-patch.ts`). One patch over several files is **one** Edit/Write card whose own fields describe only the first file, with `input.files` listing all of them — read `files`, or every file after the first is invisible. And the patch is on disk before PPM hears of it, so its "before" is the diff reverse-applied (`reverse-unified-diff.ts`), which refuses rather than guesses when a hunk does not match.
