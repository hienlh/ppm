# `src/web/components/remote-desktop/`

## Gotchas

- **`preventDefault()` on the Ctrl+V keydown cancels the `paste` event, and that is the whole reason clipboard sync is shaped the way it is**: `use-remote-input-capture.ts` preventDefaults *every* keydown so no keystroke also acts on the browser — and `paste` is a default action of that keydown, so with the guard in place it simply never fires. Measured, not reasoned: with the exemption removed the keydown count still rises and the paste count stays flat. On an insecure origin (PPM's usual LAN deployment) `navigator.clipboard` does not exist at all, so that event is the *only* way to read the client's clipboard — hence Ctrl/Cmd+V is the one combo swallowed rather than forwarded, and the **server** delivers the paste keystroke itself once the clipboard write has landed. Forwarding it instead loses the race by construction: keydown order is Control, then V, then `paste`, so the host would be pasted before the text ever arrived. Three more measured details. A focused `<canvas tabindex=0>` **does** receive `paste` (the event targets the canvas; no wrapper needed). **Ctrl+Shift+V also fires `paste`**, which is what makes the two distinguishable — and the distinction is load-bearing, because a terminal pastes on Ctrl+Shift+V and reads a plain Ctrl+V as the literal quoted-insert `^V`, so the client sends a shift flag and `pasteComboCodes` presses what the user actually pressed. And Chromium reports a paste into the mobile hidden input as `beforeinput`/`insertFromPaste` with the text in **`data`** and a *null* `dataTransfer` — the opposite of what the spec's contenteditable case describes — so the portable source is `clipboardData` on the `paste` event, which is what `use-remote-desktop-virtual-keyboard.ts` listens for (and `preventDefault()` there is what stops the `beforeinput` double-insert). Host→client then needs `navigator.clipboard.writeText`, which is secure-context only *and* rejects on an unfocused document even where it exists, so the fallback is a real click running `execCommand("copy")` over a textarea that must be off-screen but still **rendered** — `display:none`/`visibility:hidden` give an empty selection, and `execCommand` then copies nothing while still returning true.
- **Every in-session setting is one of three kinds, and picking the wrong kind is how a menu item does nothing**: the viewer's toolbar (RustDesk's `_DisplayMenu`, ported) mixes settings that cost a **capture respawn**, settings that are **pure CSS**, and settings that are **only the absence of a listener** — and each has its own failure shape. (1) The remote cursor is burned into the frames by the grabber, so it is a startup flag with a different name per grabber (`-draw_mouse` for gdigrab/x11grab, `-capture_cursor` for avfoundation) and changing it means stop-wait-respawn, which is what `restartCapture` is for now that `applyPreset` is not the only thing that needs it. It rides the **`auth`** message rather than its own `cursor` one, or every connect would respawn ffmpeg ~400 ms after the first frame; only an explicit `cursor: false` hides it, so an older client still gets the pointer. (2) The scale modes are CSS, and `adaptive` is deliberately the one that computes *nothing* — `canvasCssSize` returns null and the canvas keeps `max-h-full max-w-full`, the path the viewer has always been on. The two traps there are both silent: `max-width: 100%` **beats** `width: 3440px`, so leaving the fit classes on makes `original`/`custom` no-ops (the mode switches, the menu ticks, the picture does not move), and centring an oversized child with `justify-content: center` puts half the overflow *before* the scroll origin where no scrollbar reaches it — `m-auto` is the fix, because auto margins centre only while there is free space. Overlays must also stay *outside* the scroll container or they scroll away with the picture. `tests/unit/web/remote-desktop-scale-layout.test.ts` pins all three. (3) Clipboard sync off is implemented by passing **no** clipboard hooks: `use-remote-input-capture.ts` then stops exempting Ctrl+V from `preventDefault` and forwards it as an ordinary keystroke, so the host pastes its own clipboard — which is exactly RustDesk's "Disable clipboard" behaviour and needs no server flag. It still needs one guard on the *inbound* path, though: the client's own `clipboardRead` is delayed 350 ms, so a host reply can land after the toggle went off, and "off" has to mean the host's text never reaches this device. Last, scale modes are desktop-only on purpose — the mobile viewer's pinch-zoom stage already owns the transform continuously, and its `object-contain` + `h-full w-full` canvas is load-bearing for hit-testing.
- **The scale slider is piecewise around a pivot, and the resolutions menu is four items that are usually all hidden**: `custom_scale_base.dart` maps the track so **100% sits at 1/3 of it** (5–1000% overall, a 0.006 detent snapping to the pivot, ±1 percentage point per nudge, 300 ms debounce) — laid out linearly, 100% lands a tenth of the way along where it cannot be hit. Then `_ResolutionsMenuState.build` gates the whole submenu on `keyboard && (virtualDisplay || resolutions.length > 1) && currentDisplay != all`, and every extra item on its own condition: **Original** only once the session has moved the host off it (`isOriginalResolutionSet && !isOriginalResolution`), the **custom w×h inputs** only for a *virtual* display, one shared divider only when something above it is visible, and **Fit local** only when `_getBestFitResolution()` finds a host mode matching the client's screen **exactly** — no nearest, no letterboxed approximation, because offering 1920x1080 to a 1366x768 client puts the picture back on the scaler the item exists to avoid. So on most client/host pairs Fit local is *absent*, which reads as a missing feature and is the port being faithful. Two details in `fitLocalMode`: the comparison is by **size**, not mode id, or a host on another timing of the size the client already has is offered a switch with nothing visible to show for it (this host sits on 3440x1440@60 while advertising @100, so it is the normal case); and the local screen is the client's **CSS** pixels — RustDesk's web branch divides physical by `scaleFactor` and a browser's `screen.width` already is that number, where physical pixels would land the picture at half size on any 2x display.
