# `src/web/lib/`

## Map

- `src/web/lib/icons.ts` + `src/web/lib/icons.generated.tsx` + `src/web/lib/fluent-icon.tsx` — the product icons (Fluent System Icons 20px Regular, MIT, microsoft/fluentui-system-icons) for the app's own chrome. Every UI icon is imported from `@/lib/icons`; regenerate with `bun scripts/gen-product-icons.ts` after editing its `MAP`
- `src/web/lib/file-icons.tsx` + `src/web/lib/file-icon-name.ts` + `src/web/lib/file-icons.generated.ts` + `src/web/styles/file-icons.generated.css` — the file icon theme (real `vscode-icons` artwork, MIT). `FileIcon` for a component slot, `fileIconElement` for the `icon: ElementType` slots (tab bar, command palette, both through `src/web/lib/tab-type-icons.ts`). Name resolution is the pure half in `file-icon-name.ts` (importable under `bun:test`); the framework preset comes from `src/web/stores/project-framework-store.ts`. Regenerate with `bun scripts/gen-file-icons.ts`

## Gotchas

- **A Monaco model in PPM is not named after its file**: the editor mounts `<Editor value=... />` with no `path`, so Monaco names models `inmemory://model/N`. A language server has never heard of that, and the `file:` URIs it answers with match no model — so an unrewritten request makes the server answer about a document it was never given, and an unrewritten response makes Monaco treat the open file as a different one (go-to-definition inside the current file tries to *open* it, and diagnostics attach to nothing and never appear). `src/server/ws/lsp.ts` rewrites both directions, including URIs used as object *keys* in a workspace edit's `changes`.
- **Standalone Monaco's F12 into another file hijacks the current editor**: its default editor service, once a model exists for the target, swaps that model into the editor you are in. The tab keeps its old title and its old dirty state while showing another file's contents. `lsp-navigation.ts` replaces the binding and opens a real tab instead. Peek and find-references are left on Monaco's bindings — they render in place and never navigate — but they need a model to exist for the target, which is what the shadow models in `lsp-shadow-models.ts` are for; there is no public way to give standalone Monaco a model *resolver*, so providers create the models before returning locations.
- **Monaco's bundled TypeScript service is off entirely, and `setDiagnosticsOptions` is not what does it**: that call silences the validator but leaves all **thirteen** providers in `modeConfigurationDefault` registered, so every `.ts` file had two completion lists and two hovers — the second from a worker that sees one file with no `tsconfig.json` and no `node_modules`. It also cost a *visible* stall: answering a hover at all means fetching `ts.worker.bundle.js` (**13 MB**, the whole TypeScript compiler), and Monaco's hover widget merges every provider and shows "Loading…" until the last one replies — so the real server's answer rendered in milliseconds and then sat behind a spinner. `setModeConfiguration` is the call that unregisters them (`monaco-builtin-typescript.ts`, asserted against Monaco's own default list so an upgrade adding a provider fails a test). Consequence, accepted: a buffer the LSP cannot serve — untitled, external, inline — falls back to word-based suggestions only.
- **A button in a Monaco hover is a `command:` link in *trusted* markdown, and trust is all-or-nothing unless you narrow it**: a hover can only contain markdown, so the blame hover's actions are `[label](command:id?args)` links reaching ids registered with `monaco.editor.registerCommand`. The renderer *strips* those links unless the `IMarkdownString` is trusted — and `isTrusted: true` allows **every** command on the page's global registry. That hover embeds a commit message, so anyone who can land a commit could write `[click](command:...)` in one and have it render as a working button. Both defences are needed and both are in `blame-hover.ts`: `isTrusted: { enabledCommands: [...] }` (an array is honoured by `toAllowCommandsOption`), and escaping the message so it cannot form a link at all. `supportHtml` stays **off** — the avatar is `![](data:image/svg+xml,...)`, which renders inline at its intrinsic size, so no HTML has to be allowed for it. Escape `<` and `>` too: with `supportHtml` off the renderer does not leave an unknown tag alone, it drops the tag and keeps the text, so a message mentioning a literal `<script>alert(1)</script>` displayed as `alert(1)` — the message silently rewritten in the one view meant to show it verbatim.
- **Monaco hit-tests the gutter by x, and sizes its glyph margin in lanes**: standalone Monaco ships `glyphMargin` off (`editor.api2.js`), and the code-action lightbulb Monaco puts there when its line has no room is then drawn nowhere. Turned on, the margin is one line height per glyph *lane* in use, so the bulb fills a single 19px lane flush against the editor's edge. Moving it right with CSS looks correct and is a bug: `_hitTestMargin` tells glyph margin from line numbers by the x coordinate alone, so a bulb drawn over the line-number column still opens its menu and the same mousedown selects that whole line, replacing the selection the menu was opened for (measured: `[1,7 -> 2,8]` became `[1,1 -> 2,1]`). `monaco-lightbulb-gutter.ts` widens the margin instead, with two empty glyph-margin widgets. Three traps, all silent. Monaco draws one glyph per (line, lane), highest zIndex first and widgets winning ties, so at zIndex 0 the left widget hid the bulb on line 1. A `persistLane` *decoration* would hold the lanes as well, but any glyph decoration on the bulb's line makes the lightbulb give up the gutter and draw itself over the text. And the width follows the line that uses the most lanes, so both are held on the same line — one lane held on its own widens nothing. Separately, Tailwind's preflight `* { box-sizing: border-box }` makes Monaco's `.action-widget` 8px narrower than the row it measured, which cut the longest code action off with an ellipsis.
- **A file icon theme is five separate traps, and every one of them fails silently**: PPM draws the real `vscode-icons` artwork, vendored at build time by `bun scripts/gen-file-icons.ts` into `src/web/lib/file-icons.generated.ts` (the name → glyph tables) and `src/web/styles/file-icons.generated.css` (one `background-image` class per glyph). Both are committed; re-run the script after editing its lists, and `tests/unit/web/file-icons.test.ts` fails if the two files drift, because a name with no class renders a correctly-sized span of nothing. First trap: `width`/`height` **do not apply to a non-replaced inline element**, so the icon span needs `inline-block` — the trees are flex rows and blockify it for free, while the tab strip wraps its icon in a `<span class="relative">` for the notification dot and there the icon measured 0×0 and simply was not there. An inline `<svg>` would have worked without saying so, which is why this only broke in one place. Second: `vscode-icons-js` answers with the **light-theme** drawing for 143 glyphs and offers no way to ask for the other one (`getIconForFile("a.json")` is `file_type_light_json`, full stop), and those are darker ink meant for a light workbench — `file-type-light-toml` has no `fill` at all, i.e. black on black. The generator canonicalises the class to the theme-independent name and emits the light drawing as a `:root.light` override, which costs +1.2 KiB brotli for +100 KiB raw because the two bodies differ by a colour and brotli collapses the duplication. Third: the *mapping* is not the artwork's package. It is built from the extension's own `src/iconsManifest` (pinned tag + SHA-256 per file), because the third-party `vscode-icons-js` repackaging lags it badly — its table of multi-dot extensions holds **41** entries against the manifest's 127 — and it has never held `controller.ts`, `module.ts` or `service.ts` in any of its tables, which is why `app.controller.ts`, `app.module.ts` and `app.service.ts` drew the plain TypeScript glyph while the Nest artwork sat unused in the bundle. It is still read *second*, and that is not laziness: the manifest associates a great many types by **VS Code language id** and nothing else (the `dotenv` entry has `extensions: []`; `.cc`, `.htm`, `.conf`, `.kts` reach their icon only because the editor already knows which language owns them), so a manifest-only port silently lost 36 names that previously had an icon. Three consequences. The sources cascade **per key, not per table** — merging first and resolving after loses a key outright when the winning source names a glyph that is missing or over budget, which is how `cargo.lock` ended up blank while the second source's answer sat right there. The manifest's *language* layer ranks **below** `vscode-icons-js`'s flattening of VS Code's real associations, because `knownExtensions` turns "this language is known by .css" into "a .css file is this icon" and `tailwindcss` also claims `css` and sorts after it — every stylesheet in the app came out with the Tailwind logo. And the legacy tables answer with `file_type_light_*` names too, so the `light_` prefix has to be stripped there as well or trap two comes back through the side door. Fourth, and the reason `.service.ts` needs a project to answer it: `nest_*` and `ng_*` ship `disabled: true` upstream, behind two presets that are **mutually exclusive** — they claim the same six suffixes (`module`, `service`, `guard`, `pipe`, `interceptor`, `controller`) and `ng_` sorts after `nest_`, so enabling both hands a NestJS repository the Angular artwork. They are emitted as *overlays* and `project-framework-store.ts` picks one per project from a `package.json` dependency; `FileIcon` subscribes rather than taking a prop, because two of the eight call sites go through `fileIconElement`, which hands out a component with no project in scope. Fifth: a byte budget cuts by weight, not by worth. At 1800 bytes it dropped `file-type-reactts` (1833) and with it every `.tsx` file in a TypeScript repository, plus `.jsx`, `.go` and `.rs`. And measure the right number: the generated stylesheet is big enough that the bundler gives it its own chunk (`assets/file-icons-*.css`, 382 KiB brotli for the full 1193-glyph port), which is outside the service worker's `globPatterns` — so it never shows up in `precache N entries` and only `precompress-web.ts`'s `.br` sibling tells you what it costs.
- **A Monarch `/$/` rule never runs, so a line-oriented grammar may not use states at all**: Monarch's per-line loop ends the moment the position reaches the end of the line, which means the idiomatic-looking `[/$/, { token: "", next: "@popall" }]` is dead code — the state entered mid-line is *never* left, and it carries into every following line. The `dotenv` grammar (`src/web/lib/monaco-dotenv-language.ts`, since Monaco ships no `.env` language and neither does VS Code) first used a `@value` state entered on `=`; from the first assignment on, the whole file tokenized as a value, so `#KEY=off` came back `string` — the one case the language existed for, still broken while every line *looked* coloured. Everything has to happen in `root`, the way Monaco's own `ini` does, and the test forbids a `next:` outright. Two consequences of statelessness worth knowing: a quoted value must be matched **whole** (`/"(?:[^"\\]|\\.)*"/`), which is the only way a `#` inside it is not read as a comment — at the cost of not colouring an interpolation inside quotes; and an unterminated quote falls through to the bare-value rule instead of swallowing the rest of the file. Separately, this grammar needs **no** `*-token-rules.ts` beside `diff-token-rules.ts`: its token names are Monaco's own (`comment`, `key`, `string`, `variable`, `keyword`, `delimiter`) and `monaco-adapter.ts` defines every PPM theme with `inherit: true`, so the colours arrive from the `vs`/`vs-dark` base and cannot drift from the app's themes — the test reads that pairing out of Monaco's own theme table rather than trusting it. Last trap, when verifying any of this in a browser: a standalone Monaco has **one global theme**, so two editors cannot show two themes at once (the second `create` silently retints the first), and sampling colours right after `setTheme` reads the *old* `mtk` class indices against the new palette — `string` measured as `#FF0000`. One editor, one reload per theme. Do not be misled by a `dotenv-*.js` chunk in the build output: that is shiki's TextMate grammar for a fenced `dotenv` block in markdown (`@shikijs/langs`, reached from `markdown-code-block.tsx`), a separate pipeline Monaco cannot read — there is no TextMate bridge in the editor, which is why a Monarch grammar had to be written even though the repository already ships a dotenv grammar.
- **`tabSessionId()` is the only way to ask a tab for its session**: design tabs hold chat sessions too, so `type === "chat" && metadata.sessionId` makes a design session look unopened, and reopening it starts a plain chat outside design mode (`src/web/lib/tab-session-id.ts`).
- **pptxgenjs 4.x takes `rectRadius` in inches**: its typings say 0–1, but the writer converts inches into OOXML's fraction of the shorter side, so a fraction gives almost square corners. `pptx-slide-mapper.ts` converts px to inches and clamps to half the shorter side.
