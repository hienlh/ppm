# `src/web/`

## UI Rules

When creating or modifying any UI component, you MUST read and follow `docs/design-guidelines.md`, especially the **Mobile-First UI Rules** section. Key rules:
- Dialogs → bottom sheet on mobile (below `md:` breakpoint)
- No hover-only interactions — must have touch alternatives
- Touch targets minimum 44×44px
- Context menus → long-press on mobile, not tap
- Thumb zone: primary actions in bottom 1/3 of screen for one-handed use
- Always test both mobile and desktop layouts

### Reusable Adaptive Components

- **Context menus**: Always use `@/components/ui/adaptive-context-menu` instead of `@/components/ui/context-menu`. It auto-detects mobile (< 768px) and renders a bottom sheet with long-press trigger instead of radix right-click menu. Same API — just swap the import path. Sub-menus are flattened inline on mobile.
- **Mobile detection**: Use `useIsMobile()` from `@/hooks/use-is-mobile` for reactive mobile breakpoint checks.

## Map

- `src/web/components/problems/` + `src/web/stores/problems-store.ts` — the Problems panel: a dock tab (`DOCK_ALLOWED_TAB_TYPES`) fed by every mounted editor's `useLsp`, opened from the status bar counts on desktop and the editor's LSP row on mobile. Scoped to the active project because `tab-pool` keeps other projects' editors mounted for keep-alive, so their servers keep publishing
- `src/web/components/extensions/` — the webview host. `extension-webview.tsx` matches a panel to a tab and mounts its HTML as a sandboxed `srcDoc`; `webview-theme.ts` injects PPM's applied theme into it (mode attribute + token block) and forwards later theme changes by `postMessage`
- `scripts/gen-nerd-font.ts` + `src/web/styles/nerd-font.generated.css` + `src/web/styles/fonts/` — the terminal's icon glyphs (Nerd Fonts symbols-only, MIT, ryanoasis/nerd-fonts), subset per icon set so each `@font-face` is fetched only when something draws a character in its range. Regenerate with `bun scripts/gen-nerd-font.ts` after editing its `BLOCKS`; `TERMINAL_FONT_FAMILY` in `src/web/lib/editor-font.ts` is what names the family, and `use-terminal.ts` is what invalidates xterm's glyph atlas when a face lands

## Gotchas

- **An extension panel only gets a tab if a browser tab asked for it**: `use-extension-ws.ts` creates a tab for `webview:create` only when `locallyDispatchedViews` holds a matching entry, i.e. when *this* client dispatched the command. A panel the extension opens on its own initiative exists server-side with no tab to show it. To open one panel from another, call `window.openTab("extension", …, { viewType })` instead — `extension-webview.tsx` then sees a tab with no panel and dispatches the command itself, which *is* a local dispatch. The recovery dispatch forwards only the project path, so any other argument has to be stashed for the target panel to pick up (`packages/ext-git-graph/src/panel-nav.ts`). The command id and the viewType must also be identical: both are turned into a tab slug by stripping a trailing `.view`, and a mismatch silently yields no tab.
- **Standalone Monaco can never turn semantic highlighting on from a theme**: `StandaloneTheme` hardcodes `semanticHighlighting = false` and never reads it from the `defineTheme` data (`IStandaloneThemeData` has no such field), while the `semanticHighlighting.enabled` option defaults to `'configuredByTheme'` — so tokens are fetched, decoded, and change nothing. The only switch is the editor option set to `true` (`code-editor.tsx`). Colours then resolve through the *same* rule trie as TextMate scopes: `getTokenStyleMetadata` joins the type and its modifiers with dots (`variable.readonly.local`) and `ThemeTrieElement.match` falls back segment by segment, so a type with no rule lands on the theme's default foreground — i.e. plain text where the regex tokenizer had colour. `src/web/theme/semantic-token-rules.ts` is that table, and it must cover names outside the specification: `typescript-language-server` sends **`member`** for methods, one of the most common tokens in a TS file.
- **Hovering injected text does reach the decoration under it, and Monaco has no `diff` language**: an `after` injected-text annotation sits past the line's last column, and `ContentHoverComputer._getLineDecorations` relaxes its column check by one character *only* for `showIfCollapsed` decorations — which is what makes the blame hover work at all, and why that flag is load-bearing rather than cosmetic. `editor.action.showHover` opens the same hover from the cursor, which is the touch path (gated on `hover: none`, not on a width breakpoint; the mouse target's `injectedText` would identify the tap exactly but is not in Monaco's public typings, so the handler goes by column). Separately: Monaco's 91 basic languages include no `diff` — VS Code's comes from a bundled extension — so a fenced diff block runs the tokenizer and comes back entirely `mtk1`, the theme's default foreground. `monaco-diff-language.ts` registers one and `theme/diff-token-rules.ts` colours it; a Monarch rule whose token name has no theme rule is the same silent no-op as an unmapped semantic token, and a test pairs the two so neither can be added without the other.
- **A font stack is a wish list, and on Linux it usually loses**: `-apple-system`, `BlinkMacSystemFont` and `Segoe UI` all miss there, `Menlo, Monaco, Consolas` misses too, and the generic fallbacks resolve through fontconfig to Liberation Sans — or, for a bare `sans-serif`, to Liberation *Serif*. Nothing errors: the app was simply set in an Arial clone and the editor in whatever `fc-match monospace` answered, on the platform PPM is most often self-hosted on. The first entry of every stack is now a face `main.tsx` actually imports (Geist, Monaspace Argon, Monaspace Krypton via `@fontsource*`), and `tests/unit/web/editor-font.test.ts` pairs the two, because a stack naming a font nothing ships reads identically to the fixed version in review. Four things are load-bearing: ghost text may only use a *different Monaspace family*, never a different typeface, because Monaco places every character at column times character width and a family with another advance slides out of the grid; that override needs `!important`, since Monaco's own `.monaco-editor .ghost-text-decoration` rule is the same specificity and its stylesheet is appended by the AMD loader after the bundle; xterm bakes the cell size and glyph atlas from `ctx.font` at `open()`, so a terminal opened during the first paint keeps the fallback resolved then for the whole session unless it re-measures on `document.fonts.ready`; and the Nerd Font the terminal asks for first is now bundled as icons only, per block (the bullet below). Fonts cost nothing until used (`@font-face` is fetched per `unicode-range`, on demand), stay out of the SW `globPatterns`, and must stay out of `COMPRESSIBLE` in `precompress-web.ts` — `woff2` is already compressed.
- **Icons come from `@/lib/icons`, never from `lucide-react`, and mixing the two is invisible until you look twice**: the app's chrome is Fluent System Icons at 20px Regular (the set `miguelsolorio.fluent-icons` puts over VS Code's product icons), vendored by `bun scripts/gen-product-icons.ts` into `src/web/lib/icons.generated.tsx` and built on the one component in `src/web/lib/fluent-icon.tsx`. 207 of the 222 names resolve; the other 15 stay on lucide on purpose and `tests/unit/web/product-icons.test.ts` pins that list, because "fix the missing icon by falling back" is how an icon set stops being one. Four things to know. The two sets share almost no vocabulary — lucide's `X` is Fluent's `dismiss`, `Check` is `checkmark`, `Trash2` is `delete`, `Plus` is `add`, `RefreshCw` is `arrow-sync`, and only 72 names kebab-case straight across — so `MAP` in the script is a hand-checked table, and every entry is verified against the collection at generation time rather than trusted. The glyphs keep their **20px** viewBox rather than being re-boxed to lucide's 24: Fluent's outlines are drawn for that grid, and the app sizes icons with Tailwind `size-*` classes anyway, which beat the width/height attributes because they are CSS. `strokeWidth` is accepted and *dropped* — these are filled outlines with nothing to weight, and spreading it would put a dead attribute in the DOM and make React warn about `absoluteStrokeWidth` on every render. And the identifying hook is `data-icon="<name>"`, not a class: lucide put the same information in `class="lucide lucide-circle-check"`, which is what let a tool-card test assert "this card is spinning" by string-matching the markup — an attribute keeps that possible without offering stylesheets a class name to start depending on. Related and separate: the *file* icons are a different system (`@/lib/file-icons`, the entry above), because those are full-colour artwork with no `currentColor` to inherit.
- **Screen wake lock needs a secure context**: `navigator.wakeLock` does not exist at all over plain HTTP, so reaching PPM at `http://<lan-ip>:<port>` silently disables "keep screen awake" — the very setup (a tablet on the LAN) it was built for. Only HTTPS and `localhost` qualify. The lock is also released by the browser on *every* hide, so `src/web/hooks/use-wake-lock.ts` re-acquires on `visibilitychange` and drops its handle on hide rather than waiting for the `release` event, whose ordering against `visibilitychange` is undefined.
- **A long-press must be disarmed on `touchcancel`, and leaving it out looks like nothing**: the pattern is a timer armed on `touchstart` and cleared on `touchmove`/`touchend`, which reads as complete. It is not — once the browser decides the gesture belongs to a scroll it fires **`touchcancel`** and then delivers *no further* `touchmove` or `touchend` to that element, so the timer survives the scroll and fires into it: a context menu over a list the finger is already moving, or a tab strip entering drag mode by itself. A movement tolerance cannot save it either, because the moves it would have measured are never delivered. It reproduces on a phone and nowhere else (a mouse has no touch events, and device emulation dispatches move/end faithfully), which is how it stayed live in **seven** separate hand-rolled long-presses at once — `git-status-panel.tsx`, `ui/adaptive-context-menu.tsx`, `os-explorer/use-coarse-long-press.ts`, `hooks/use-touch-tab-drag.ts`, `layout/mobile-drawer-tab-bar.tsx`, `layout/mobile-tab-switcher-sheet.tsx`, `layout/project-bottom-sheet.tsx`. `tests/unit/web/long-press-touchcancel.test.ts` fails any file that arms a timer from `onTouchStart` without naming `onTouchCancel`. Two related traps in the same shape: a hook that returns handlers has to *return* the cancel one and every forwarding component in between has to pass it on (`use-touch-tab-drag` → `tab-bar` → `draggable-tab` is three files for one prop), and the timer needs clearing on unmount — the git panel refreshes its file list on every save, so a row can vanish mid-press and open a menu belonging to no row.
- **A blob URL is not stable for the life of the thing it previews**: the composer creates one from the image as pasted, downscales, then revokes the first and points the chip at the reduced copy — and `URL.revokeObjectURL` makes an open viewer render a *broken image* with no error, no console warning and nothing to say why. So `attachment-chips.tsx` keeps a `Map` of every preview URL it has handed to the lightbox against the attachment it belongs to: a URL that was replaced is followed, and one whose attachment is gone closes the viewer. Keyed by URL rather than by remembering one "currently viewing" id, because the overlay's arrow keys move between images without telling the component, and an id stops describing what is on screen the moment they are used. Related: the lightbox's gallery is collected from the **DOM** (`collectGallery`), so a row of thumbnails needs `GALLERY_ROOT_ATTR` on the container *and* `GALLERY_ITEM_ATTR` on each `<img>` — miss either and the viewer opens with dead arrows and no sign a second image was ever attached.
- **A prompt's icons are Private Use Area codepoints, and a font that arrives late draws nothing at all**: a themed shell prompt takes its separators, git status and language badges from the PUA, so on a machine with no patched font every one of them was tofu while the `↑39 ↓15` between them rendered — those two are real Unicode, and that asymmetry is the whole diagnosis. `scripts/gen-nerd-font.ts` vendors the symbols-only face (version and SHA-256 both pinned; the single file from the repository tree is byte-identical to the one inside the release tarball, so no `tar`/`xz` is needed) and splits it into **fourteen** `@font-face`s, one per icon set. The split *is* the optimisation and it is load-bearing three times over: a face with no `unicode-range` is a candidate for all text and downloads unconditionally — all 1.14 MB of it; two faces claiming one codepoint fetch a second 500 KiB file to draw a glyph already in hand; and Vite's 4 KB `assetsInlineLimit` base64'd the four *smallest* faces straight into the entry CSS, which is the one file the SW precaches, so the rarest sets became an unconditional download for everyone (hence the function form excluding `woff2`, which made the boot shell 9 KiB smaller than before the font was added at all). The family name is PPM's own rather than `Symbols Nerd Font Mono` because a `@font-face` shadows a same-named system font *completely* — naming the real one would replace a full local install's 10,624 glyphs with this subset's — and it sits behind the installed names but ahead of Monaspace, which is safe only because it contains no letters or digits for ordinary text to stop at. Then the timing, measured rather than assumed: a canvas `fillText` **does** start the fetch (0 → 1 request; setting `ctx.font` alone does not), the load **does** fire `FontFaceSet`'s `loadingdone`, and the tofu it drew first is **permanent** — xterm bakes glyphs into a texture atlas and nothing repaints it, so ink was byte-identical 1.8 s after the face finished loading and only changed on a redraw. `use-terminal.ts` hangs `clearTextureAtlas()` + `refresh()` on `loadingdone` for the terminal's whole life; `document.fonts.ready` cannot do it, because it resolves long before a prompt first draws a PUA character and triggers the fetch. With the listener's body removed the glyph rasterisations after a face landed were +0, with it +14. Last trap, and it is the one that makes this untestable locally: after the stack is exhausted the browser asks **fontconfig** for any font with the codepoint, and a dev box with Nerd Fonts installed answers for all of them — so the webfont is never requested, a local screenshot proves nothing, and the bug reproduces only where no such font exists. Verify by forcing each face with `document.fonts.load()` and asserting the request that follows is that block's file.
- **A `DropdownMenu` used as a row's context menu takes the row's tap away, and the adaptive one gives no tap back**: a dropdown trigger opens on *click*, so on a touch screen the gesture that opens it is the same one that would have activated the row — the Source Control panel's folder rows could not be expanded on a phone at all, because tapping one opened a menu over it. `@/components/ui/adaptive-context-menu` is the fix (bottom sheet + long-press below `md`, radix right-click above), but it only *suppresses* the click that follows a press: it has no tap handler of its own, so whatever the tap should do has to be a real button inside the trigger. That is also what removes the hand-rolled "was that a tap or a press?" timer, which is where the `touchcancel` class of bug lives. Two details when converting: mark a destructive item with `variant="destructive"` rather than a `text-destructive` class, because the class only reaches the radix half and the sheet takes its colour from the variant; and put `select-none` on the trigger's child, or a long press starts a text selection under the sheet it opens.
- **An ANSI palette's neutral ends sit on top of the background, and the fix is not in the palette**: two of the sixteen slots are *defined* to be extremes, so a light theme's `white`/`brightWhite` and a dark theme's `black` land on the background — 1.03–1.18:1 across PPM's six built-in themes, i.e. invisible rather than merely dim. It is not a theoretical slot either: oh-my-posh writes its second prompt line in plain **SGR 37**, correct on the dark terminal it was designed for, and that line was absent on every light theme. Recolouring the slot cannot fix it, because the same `white` is also the text *on* a coloured powerline segment where white is right — only a per-cell decision can tell the two uses apart. `minimumContrastRatio` is xterm's, it defaults to **1 (do nothing)**, and VS Code ships 4.5; it adjusts the foreground against each cell's real background, so segments render byte-identically and only text on the bare background moves. Set it as a *terminal* option, not via a renderer: the WebGL addon is skipped on touch devices, which is where this was reported from. Two traps when measuring a prompt: parse `38;5;`/`37`/`97` as well as `38;2;` truecolor, or plain-ANSI runs read as "no colour set" and the real culprit is invisible to the tooling too — and a `%{`…`%}`-quoted zsh prompt has to have those markers stripped before it is written to a terminal, since the shell normally eats them. `tests/unit/web/terminal-contrast.test.ts` pins the hazard and the mitigation together.
- **xterm stays silent about a selection it already reported, even after clearing it**: `onSelectionChange` fires from `_fireEventIfSelectionChanged`, which compares against the last selection it *reported* — and `clearSelection()` fires the event without resetting that record. xterm itself clears on resize, on a buffer switch and whenever the user types with something selected, so selecting the same text again afterwards reports nothing, and anything driven by the event alone (the terminal's Add to chat bar) silently does not appear. Found by an e2e that selected the same rows twice; `terminal-selection-chat.tsx` also reads the selection on the mouseup that ends a press in the terminal. Related: `getSelectionPosition()` is typed as 1-based and returns 0-based columns and buffer rows, end column exclusive.
- **An overlay on a vendored glyph assumes that glyph is empty, and an icon set migration silently breaks that**: the streaming chat tab draws three bouncing dots absolutely positioned over its 16px bubble icon, which was correct against lucide's hollow `MessageSquare`. Fluent's `chat` is the same bubble with **two message lines drawn inside it**, so after the migration the dots landed on the upper line in the same `currentColor` and the three fused into one lumpy bar — a static-looking smudge at the size a tab renders, reported as a broken animation rather than a wrong glyph, because the dots really were still bouncing. The fix is `chat-empty` (exported as `MessageCircle`), whose two subpaths are byte-identical to `chat`'s first two: same outline, nothing in it. Two things generalise. A glyph's *subpath count* is the cheap test for "does this draw anything inside itself" — `tests/unit/web/tab-streaming-indicator.test.ts` asserts the host glyph contributes exactly the outer edge and its hole, so a MAP edit or a regeneration cannot put a lined glyph back under the dots; and freezing a CSS animation with `animation-play-state: paused` plus a *negative* `animation-delay` renders any phase of its cycle, which is how a bounce this small is compared before and after at all. Note also that `isStreaming` is safe to branch an icon on only because both call sites read `sessionId` exclusively for `type === "chat"`.
- **A filename column has to ellipsize from its *start*, and only `dir="rtl"` + `<bdi>` does it without leaving a mark**: `text-overflow: ellipsis` cuts the end, which in a list of source files is the only part that differs — `remote-desktop-capture.ts`, `remote-desktop-capture-input.ts` and `remote-desktop-encoder-args.ts` agree for **23 characters**, so seven Source Control rows all rendered as `remote-desktop-…` and the panel could not say which file it was listing. Three approaches fail before the fourth, and none of them fails loudly: splitting the name and pinning the tail beside an ellipsized head opens a ragged gap mid-row, because flex hands the head a fractional width while the ellipsis lands on a whole character — and `text-align` does **not** close it (measured; alignment does not apply to overflowing content); a fixed-length tail cuts mid-word into fragments that mean nothing (`…rgs.test.ts`); and the U+2066/U+2069 isolate *characters* render correctly but land in `textContent`, so a copied filename carries invisible codepoints. `<bdi>` inside a `dir="rtl"` box is the one that leaves the text clean (`StartEllipsis` in `git-status-panel.tsx`), and the isolate is load-bearing rather than tidy: outside one, the `.` of `.gitignore` is a neutral character at a run boundary, takes the paragraph's direction and renders as `gitignore.`. A dimmed path prefix in the same box has to be **one inline flow** inside the `<bdi>`, not two flex children, or the row's `gap` opens a space inside the path (`web/ components`). Related: the tree's own pure functions live in `src/web/lib/git-file-tree.ts` rather than in the panel, because importing the component reaches the zustand stores, which read `localStorage` at module scope and throw under `bun:test` — logic embedded in a component file here is untestable by construction, not merely awkward.
- **`opacity` is not a dimming level, it is a fade toward whatever is behind it — so one value cannot serve both modes**: the file explorer marked gitignored rows with `opacity-40`, which reads as a single decision and is not one. Measured against PPM's six built-in themes, that put a gitignored *filename* at **1.72–1.89:1** against the panel on the three light themes and 2.07–2.23:1 on the dark ones — unreadable on light, merely dim on dark, from the same class, so it reproduces only for whoever is on a light theme. A de-emphasised state has to be a **colour**: `--color-text-dim` is `color-mix(in srgb, var(--text-2) 50%, var(--text-3))`, which measures 3.59–5.21:1 across all six while staying visibly below `--text-2`. The file icon is then left alone entirely — those glyphs are `background-image` artwork with no `currentColor`, so an opacity on them is that same fade and nothing else, which is why the *folder* icon was the washed-out thing in the report. `tests/unit/web/explorer-ignored-contrast.test.ts` measures the hazard and the mitigation together and reads the mix out of `globals.css` rather than restating it, so the two cannot drift.
- **Half of VS Code's compact folders is worse than none of it**: joining a single-child chain into one `a/b/c` row only makes sense if it happens on the way *in*, before the intermediate row is ever drawn. PPM's `flatten-visible-tree.ts` required both paths to be in `expandedPaths`, so it fired one gesture too late: clicking a folder made the row you clicked vanish upward into its parent and shifted everything below it a level left. `depth` is the load-bearing part — it becomes `paddingLeft`, so a compacted chain indented its children by how many rows were above them rather than by where they actually sit. It also leaked into four other files as an `effectiveNode`/`effectivePath` shadowing the real one (focus, range selection, the drop target, the inline-create target). One row per directory, always; `tests/unit/web/explorer-row-per-directory.test.ts` pins it.
- **A Tailwind colour class naming a token that does not exist emits no rule, and nothing reports it** — not the build, not the browser, not review. `bg-surface-hover` was written against `--surface-hover`, which only ever existed inside the extension panels' injected stylesheet (see the webview-theme entry above, where the app is explicitly described as having no hover token). In the app it resolved to nothing, so **21** uses in the System Monitor alone were silent no-ops: no hover feedback on any Processes/Services/Apps row, and the memory composition bar, the partition bars, the Performance sidebar sparklines and the Overview per-core strip all painted their track `rgba(0, 0, 0, 0)` — a contrast ratio of **1.00** against the card, which reads as a broken component rather than a missing colour. The tokens Tailwind can build a utility from are the `--color-*` declarations in `globals.css`'s `@theme` block and nothing else; `tests/unit/web/tailwind-token-exists.test.ts` pins that set against the classes `src/web/components/system` actually uses. Two related traps in the same file: derive a hover surface from `--text`, never from `--panel`/`--panel-2`, because some themes give those two the same value; and `MetricChartCanvas`'s `grid` prop defaults to **off**, which every Performance detail page overrides and the five Overview cards did not — an idle CPU card is then a correct flat line in a blank box, which reads as a rendering fault.
- **A dialog is a CSS grid, so one unbreakable string inside it widens the whole panel — and `break-words` cannot stop that**: `DialogContent`'s implicit `auto` column takes its base size from its items' **min-content** contribution, and `overflow-wrap: break-word` is defined *not* to affect min-content size. A 79-character log line in the Services unit dialog therefore sized the column at **693px inside a 512px dialog**, and the title and the log box drew outside the panel over the page behind it — with `word-break: break-all` on the title all along, which is irrelevant because the title was never the widest item. The column is `grid-cols-[minmax(0,1fr)]` (base size zero); anything that still does not fit then overflows *itself*, which for a scroll container is a scrollbar and for text is a wrap. Two traps ride along. The close button is `absolute top-4 right-4`, i.e. over the header's **first line**, so any title long enough to reach the corner renders under the X — the header reserves `pr-8`, but only when the button is rendered (`showCloseButton &&`), since the padding would otherwise shift the `text-center` header below `sm`. And a caller's own width class is usually **dead**: the primitive caps at `sm:max-w-lg`, so a bare `max-w-2xl`/`max-w-xl`/`max-w-md` emits a rule that loses to it at every width above 640px — ~10 dialogs in the app say a width their source does not render, and the fix is to pass `sm:max-w-*`. Verify a fix by *measuring* in a browser (`gridTemplateColumns`, `getBoundingClientRect` of the title against the close button and against the panel), not by reading the classes: all three of these look correct in review.
- **A browser-cache hydrator in a lazy chunk registers after boot hydration has finished**: `hydrateProjectCache` (`src/web/lib/browser-cache/project-cache-hydration.ts`) runs once per project at boot and on `switchProject`, but `slash-items-cache.ts` loaded only with the lazy chat chunk, so it registered after the project was already marked hydrated. Its IndexedDB copy was never read, and the `/` list waited for the network after every reload, while every unit test passed. Registration now runs a late hydrator for projects that are already hydrated, and `app.tsx` imports the slash cache eagerly. A new cache owner needs the same check. Related: a new chat tab is resolved in `panel-store.openTab` rather than in the gate, because the gate's `pending` is a prop and anything it does in render or in an effect lands after the first paint.
