# `packages/`

## Gotchas

- **Extensions may only spawn `git`, `node`, `bun`, `npx`, `sqlite3`** (`ALLOWED_SPAWN_COMMANDS` in `extension-rpc-handlers.ts`) and the call *throws* for anything else. Reaching for `test`, `cat` or any other coreutil looks fine in review and fails only at runtime — where a surrounding `catch` can turn it into silently missing data rather than an error. `env` is merged over `process.env` (so `PATH` survives) except for `BLOCKED_ENV_KEYS`; `GIT_SEQUENCE_EDITOR` and `GIT_EDITOR` are not blocked, which is what makes a non-interactive `git rebase -i` possible.
- **A webview inherits nothing from the app, including which theme is on**: the iframe is `sandbox="allow-scripts"` with its own document, so none of the CSS vars `apply-theme.ts` writes to `<html>` reach it and there is no `.dark` class to read. The only question the panel can ask by itself is `prefers-color-scheme` — the *OS* setting — which is why every extension panel rendered dark inside a light app on a dark desktop. `webview-theme.ts` stamps `data-ppm-theme` on the panel's own `<html>` and appends the app's tokens as a `:root[data-ppm-theme]` block, and the panels' dark rules are written as `:root[data-ppm-theme="dark"]` plus `@media (prefers-color-scheme: dark) { :root:not([data-ppm-theme="light"]) }` — a bare `:root` inside that media query is the bug, because it cannot lose to an explicit light. Three things are load-bearing: the injected block is *appended last* and ties on specificity, so a panel rule more specific than one attribute silently wins over the app's colours; the seed goes into `srcDoc` (later changes are `postMessage`d, because rewriting `srcDoc` reloads the panel and a graph would refetch every commit — and the theme is posted again on every iframe `load`, because the tab pool moves a tab with `appendChild` and a moved iframe reloads from that same `srcDoc`, whose seed is the theme of the moment the HTML arrived); and `--surface-hover` is derived from `--text` rather than injected, because some app themes give `--panel` and `--panel-2` the same value and a hover mapped from either would be invisible in exactly those themes.
- **A webview panel has no `prompt`/`confirm`/`alert`**: `extension-webview.tsx` mounts the iframe with `sandbox="allow-scripts"` and nothing else, and a sandboxed `prompt()` returns `null` silently — no exception, no console warning. Any answer a panel needs has to be collected by markup it renders itself (`confirmHtml` in `reflog-view.ts`). The same string is a TypeScript template literal, so a backtick anywhere inside it — a `` `code span` `` in a comment is the usual one — ends the literal early and reports as a syntax error at some unrelated token far below.
- **Escaping before matching lets a pattern rewrite the text it escaped**: the git graph escaped a commit message to HTML and *then* ran the issue-link rules over the result. The default rule is `#(\d+)`, an apostrophe escapes to `&#39;`, so "Monaco's" rendered as a literal `&#39;s` with `#39` styled as an issue link — every message with an apostrophe in it, which is most of them. `commit-message-html.ts` matches the raw text and escapes only what it emits; the same order matters for the URL and bare-hash rules, which otherwise link something *inside* a URL and split it. That file also shows the way to unit-test code that lives in a webview: write it as a real typed function and inject `fn.toString()`, which Bun returns type-stripped, rather than keeping a second copy inside a template literal where every regex backslash has to be doubled. And a backtick anywhere in a comment inside those template literals — including inside a CSS comment — ends the literal and reports as a syntax error hundreds of lines away; `webview-html.test.ts` now parses the whole injected script with `new Function` so that lands as a failing test instead of a blank panel.
- **An extension is handed a path, and it resolves the PPM project by matching that path exactly**: open a git-graph panel on a sub-repository and `resolveProjectName` falls through to the directory's basename, which names no registered project — so the tab it opens builds `/api/project/<basename>/…` and 404s, while the file path it carries is repository-relative where a tab's is project-relative. `packages/ext-git-graph/src/project-scope.ts` picks the innermost project *containing* the path and rebases the file onto it, and `resolveFileTab` does both at once because resolving them separately is how one of them gets forgotten. The spawn allowlist is not in the way: `assertSafePath` accepts any directory under a registered project, so a sub-repository is a legal cwd. Related trap when testing this: the extension host's `fetch` base URL is `http://localhost:${configService.get("port")}`, **not** the port the server was actually started on, so a dev instance whose config port disagrees has every extension `fetch` fail silently into its fallback.
- **A banding rule qualified with an id outranks hover and selection**: `#commit-list .commit-row:nth-child(even)` is (1,2,0) against `.commit-row:hover` and `.commit-row.selected` at (0,2,0), so every *other* row silently stopped highlighting on hover and when selected — the kind of thing that reads as "sometimes it doesn't work". Zebra striping has to be written at the same specificity and earlier in the file, and a test asserts both. In the same stylesheet, the phone block (`@media (max-width: 640px)`) must come after the `@media (pointer: coarse)` block and after the two width tiers (900px drops date and hash, 760px drops changes), because the later block is what decides a tie.
- **The Git Graph's column widths are one number owned by JS, and the message column is what pays for getting it wrong**: the commit row is a flexbox whose six other cells are all pinned by a `min-width`, so `.col-message` is the only thing that can shrink — and it was written `min-width: 0`. The graph column was then set to the SVG's *intrinsic* width (`28 + (lanes − 1) × 22`), with no relation to the panel, so from about 22 parallel lanes up in a 1020px panel the message column was zero pixels wide and the columns behind it were clipped away with `overflow-x: hidden` over them. The fix is a cap (`graphColCap()` measures the header's own cells, so a hidden column hands its pixels over without anything having to know which columns exist) plus a floor (`MESSAGE_MIN_W`, interpolated into both the CSS and the script from one constant). Three things are load-bearing. A cap without a **clip** is not a fix: the SVG is `position: absolute` and the rows are static, so it paints *above* them — an uncapped overlay draws branch lines through the messages, which is why `#graph-clip` exists and why the clip box is offset by the row's 6px padding while the 2px the drawing sits in from there moved onto the SVG (both on the box and it ends 2px into the message). There is nowhere to put a real scrollbar, which is why what the clip hides is reached by **dragging the graph**: the clip is as tall as the whole history, so `overflow-x: auto` on it puts the bar thousands of pixels below the viewport, and a strip inside the 24px header row lands its thumb across the word "Graph" (a strip *under* the header works, and costs a row of its own that the reader did not ask for). The drag needs one non-obvious line: a row's `.col-graph` is an empty spacer in a row that centres its cells, so it is **0px tall** and `elementFromPoint` there answers with the row — `align-self: stretch` is what makes the cell the thing under the pointer, and it must not reach the header's cell, which has a label that then lifts off the other headings' line. The rest is a movement threshold (sideways, past 4px, or it is the click that opens a commit), `touch-action: pan-y` so a finger scrolling the list still belongs to the browser, and a capture-phase `click` handler, because a pan ends over a row whose own handler would otherwise open it. And the cap is a share of the panel, so it needs a `ResizeObserver`: nothing re-renders the graph when a window is dragged, and the old cap then quietly outlives the width it was computed for. Verify with `bun tests/e2e/git-graph-narrow-layout.ts`, which measures a synthetic 40-branch history in headless Chrome — a CSS assertion cannot tell you that a column ended up 240px wide.
- **`vscode.languages` and every editor API are absent for extensions**: no `activeTextEditor`, no `setDecorations`, no hover providers. Anything GitLens-shaped that wants to annotate code has to render its own view in a webview panel.
- **Since git 2.48, `git fetch` creates `refs/remotes/origin/HEAD`, and `%(refname:short)` prints it as `origin`**: a ref list that does not skip symbolic refs (`%(symref)` set) grows a branch called "origin" and an extra label on the default branch's commit. The Git Graph showed both until it skipped them.
