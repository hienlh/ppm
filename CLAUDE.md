# CLAUDE.md

## Project

PPM (Project & Process Manager) — a web-based IDE/project manager with AI chat powered by Claude Agent SDK.

## Dev Config

Config is stored in **SQLite** (`~/.ppm/ppm.db`). Dev uses a separate DB:

- **Dev**: `~/.ppm/ppm.dev.db` — port **8081**
- **Production**: `~/.ppm/ppm.db` — port **8080**

`bun dev:server` automatically uses the dev database. On a new machine, run `ppm init` to create default config, then `ppm config set port 8081` for dev.

## Release Process

1. Commit feature/fix changes
2. Update `CHANGELOG.md` with all changes
3. Bump version in `package.json` — patch for small changes, minor/major for large ones
4. Commit: `chore: bump version to x.x.x`
5. Publish: `npm publish --access public`

## Quick SDK Tool Test

Use `test-tool.mjs` to verify SDK tool execution against any project cwd:

```bash
bun test-tool.mjs /path/to/project                    # default: echo test
bun test-tool.mjs /path/to/project "dùng thử tool bash"  # custom prompt
```

This uses `ClaudeAgentSdkProvider` directly — same env/settings overrides as production.

## PPM Directory

**Never** use `resolve(homedir(), ".ppm")`, `join(homedir(), ".ppm")`, or `process.env.PPM_HOME || resolve(homedir(), ".ppm")` directly in service code.
Always import `getPpmDir()` from `src/services/ppm-dir.ts`. This ensures test isolation via `PPM_HOME` env var.

Exceptions (intentionally use real `homedir()`):
- `autostart-generator.ts` / `autostart-register.ts` — system service paths (launchd, systemd)
- `claude-usage.service.ts` — reads `~/.claude/` credentials (different dir)
- `fs-browse.service.ts`, `git-dirs.service.ts` — file browser starting from real home
- `ppmbot/` — bot files in real home
- `slash-discovery/` — discovers skills from real home
- `design/design-skill-install.service.ts` — installs the suggested design skill where Claude (`$CLAUDE_CONFIG_DIR/skills`, else `~/.claude/skills`) and Codex (`~/.agents/skills`) read user skills
- `named-tunnel/cloudflared-cert.ts` — `~/.cloudflared` is where `cloudflared` itself writes `cert.pem`, not PPM's directory
- `fs-credential-path-guard.ts` — refuses `~/.cloudflared` (alongside the PPM dir) on every fs read/write/transfer door
- `db-backup/db-backup-paths.ts` — snapshots live in `~/.ppm-backups` *outside* the PPM dir on purpose, so they survive a wipe of it (under an isolated `PPM_HOME` they go back inside that temp dir)

## Never Write to the Real `~/.ppm` From a Script

Ad-hoc scripts, spikes and probes **must not** touch the production database. `getDb()` opens `~/.ppm/ppm.db` for whoever asks first, so merely importing a service is enough to reach it — that is how a throwaway proxy probe once blanked the auth token and deleted every project (see `docs/lessons-learned.md`).

Before running any script that imports from `src/`:

```bash
PPM_HOME=$(mktemp -d) bun my-script.ts     # scratch database, nothing at risk
```

`src/services/prod-db-guard.ts` enforces this: only `src/index.ts` (CLI), `src/server/index.ts`, `src/services/supervisor.ts` and `src/services/edge-forwarder.ts` may open the real database. Anything else throws unless `PPM_HOME` is set or `PPM_ALLOW_PROD_DB=1` is passed deliberately. If you hit that error, **set `PPM_HOME` — do not set the override** unless writing to the user's live instance is the actual goal.

Related: `configService.save()`/`set()` throw when `load()` has not run, because an unloaded `ConfigService` still holds `DEFAULT_CONFIG` (blank token, no projects) and persisting it overwrites real data.

## Known Gotchas

Gotchas confined to one subsystem live in a `CLAUDE.md` inside its directory (`git ls-files '*CLAUDE.md'` lists them), which Claude Code loads once it reads a file there. Add new ones to the narrowest such directory; only traps that cross subsystems or would do severe damage stay here.

- **SDK .env poisoning**: Projects with `ANTHROPIC_API_KEY` in `.env` break SDK tool execution. Provider neutralizes these vars. See `docs/lessons-learned.md`.
- **File watching**: never `fs.watch(dir, { recursive: true })` on a project root — on Linux that is one inotify watch per subdirectory, `node_modules` included (it once cost 359k watches). Ignored dirs must be pruned at registration time via `src/services/file-watcher/watch-tree.ts`.
- **A file change marks the flat file index stale, and must never make a request walk the project**: `buildIndex` used to walk with `readdirSync` on the main thread while every change dropped the cache and the explorer refetched `/files/index` 300 ms later. nxsys-workspace (181k entries, 22 MB of JSON) is a 6.2 s walk, so a session writing test artefacts into it kept the event loop stopped back to back until the supervisor's health check (5 s timeout, three strikes) killed the server — and every Claude session under it. Now the walk yields every 256 entries on `setTimeout(0)` (`setImmediate` costs 0.002 ms a yield against 1.09 ms, but starved HTTP to a 16 ms p50 against 1.4 ms), a stale list is rebuilt behind the one held, a request waits for that rebuild at most `REBUILD_GRACE_MS` (1 s — enough that an ordinary project answers fresh and a file just created is in the palette on its first open), and `files:index-changed` goes out only when the rebuilt paths differ. The browser does not refetch on a change either: `file:changed` and `files:index-changed` set `indexStale`, and `ensureIndex` refreshes when the palette, the compare picker or the @-picker opens. Two traps. A rebuild runs only when a request asks for one, so a change landing mid-walk is walked again only if a request saw it (`rewalk`) — rebuilding on a timer would keep a core busy for as long as a session keeps writing. And a first walk that no longer stops the server can outlast **Bun.serve's default 10 s idle timeout** (14 s on a busy scratch server), which cuts the request off with the list nearly built; the route calls `server.timeout(req, 30)` through `c.env`, the server `app.fetch(req, server)` passed.
- **Project Claude settings**: `.claude/settings.local.json` can restrict tools even with `bypassPermissions`. Provider overrides with empty settings.
- **Transcript images live in two places**: the base64 payload sits at `message.content[].content[]` inside a tool result, but Claude Code also writes an image-shaped record at the top-level `toolUseResult` field carrying no payload. An assertion like "no `"type":"image"` remains" must be scoped to the former, or it fails against correct code.
- **Plugin items are named by location, not frontmatter**: Claude Code registers a plugin's skills and commands as `<plugin>:<path>` (`ak-engineer:ak-debug`) and only honours the frontmatter `name` for agents. Kits that self-namespace instead — AgentKit ships `name: ak:debug` — publish a name nothing can resolve. `slash-discovery` mirrors that rule and keeps the declared name as an alias; `src/server/ws/chat.ts` rewrites the alias to the canonical name before the message reaches the SDK.
- **Nested subagents are never streamed**: the SDK stamps `parent_tool_use_id` only on agents the session itself spawned. An agent that spawns another agent (a reviewer running `Skill code-review`, a planner calling researchers) produces **zero** stream events for that grandchild, so the Agent card would freeze on the forking step for minutes. Its transcript still lands in `<session>/subagents/agent-<id>.jsonl`, with a meta carrying only `parentAgentId` (raw id, no `agent-` prefix) and no `toolUseId`. `src/services/nested-subagent-spy.ts` tails those during the turn and `subagent-transcript-merger.ts` folds them in flat, time-ordered, on reload — both via `groupSubagentsByCard`, which walks the `parentAgentId` chain to the root card.
- **A compiled PPM reaches none of its own `node_modules`, and is not bun**: `bundledServerEntry` resolves the TypeScript server it ships through `createRequire(import.meta.url)`, which in a compiled binary is `file:///$bunfs/root/…` — so resolution falls back to the process's **cwd**, and the systemd unit's cwd is `~/.ppm`. Measured: started from inside the checkout it answers the real path, started anywhere else `null`, i.e. "TypeScript is not installed" on every release binary and on the unit, for a server the repository does depend on. The second half is the same trap as `<ppm> x @openai/codex app-server`: `process.execPath` is bun only from source, so spawning `[process.execPath, entry]` runs *PPM's CLI* with a script path. Anything that runs a JS entry has to go through `resolveBunPath()` (`bunRuntime()` in `lsp-manager.ts`), and `installLanguageServer` needs it too — which is why a host with no bun at all is reported as not-installed rather than started and left to fail at spawn.
- **`bun add` in a directory with no `package.json` installs into the parent**: it does not create a manifest where it was asked to. Measured — in `<dir>/sub` with a manifest at `<dir>`, the package landed in `<dir>/node_modules` and `sub` stayed empty. Anything installing into a PPM-owned directory (`lsp-install.ts`, `extension-installer.ts`) must write that directory's own `package.json` first, or the packages appear somewhere above the PPM dir and every later lookup answers "not installed".
- **A `~/.cargo/bin` proxy exists whether or not the component does, and `Bun.which` cannot see a `PATH` you just set**: `~/.cargo/bin/rust-analyzer` is a symlink to rustup, present on any rustup install — measured on a host where `rustup which rust-analyzer` answered `unknown binary`, the symlink was right there. Found on `PATH` it reports an installed server that prints that error and exits at spawn, i.e. a *broken* server instead of the missing one the Install button is offered for, so `lsp-manager.ts` asks `rustupServerPath` **before** `Bun.which` and takes rustup's 3 ms answer as both the lookup and the installed-check. The same call is the reason a test cannot fake a missing toolchain: `Bun.which` reads the `PATH` the **process started with** and ignores every later write to `process.env.PATH` (so does `Bun.spawn`'s own resolution) — only the explicit `Bun.which(cmd, { PATH })` option is live, which is what `installToolPath` passes. A child gets the same snapshot: `Bun.spawn` without `env:` passes the environment the process *started* with, so a variable written to `process.env` afterwards (a `beforeEach` setting one, say) never reaches it, under `bun test` too. Pass `env: process.env` or an argument; `tests/fixtures/fake-tailscale.ts` takes its state file as an argument for that reason.
- **The service worker's precache can silently undo any download saving, and both compressions are needed**: `injectManifest` defaults to precaching *everything* in the build output, so the first visit fetched 488 files / 33.3 MB — including the 12.7 MB TypeScript worker that `monaco-builtin-typescript.ts` had just made unnecessary to ever load. A saving measured in the network tab of a warm page is not a saving; measure `precache N entries (X KiB)` in the build output too. `globPatterns` now lists only the boot shell (9 entries / 1.08 MB) with everything else on a runtime `CacheFirst`. Separately, `scripts/precompress-web.ts` writes **both** `.br` and `.gz` siblings and `static-encoding.ts` picks one: brotli alone is not enough, because browsers advertise `br` only on a **secure origin** and PPM is routinely reached over plain HTTP on a LAN. And Monaco is staged locally by `scripts/copy-monaco.ts` with `loader.config({ paths: { vs: "/assets/monaco/vs" } })` — the default is jsdelivr, which means no editor offline and a third party told which files are opened. `vite build` empties `dist/web`, so `copy-monaco` and `precompress-web` must run *after* `build:web` (running `build:web` alone leaves an installed PPM with no Monaco at all).
- **`FileSink.write()` consumes the whole chunk and returns a number that is not how much of it went in**: the careful-looking `while (off < buf.length) { off += await sink.write(buf.subarray(off)) }` is therefore a loop that re-sends the tail. Measured against `cat`, one 4,924,800-byte frame produced eleven `write()` calls each answering **475072** while everything had already been buffered, and the child received **28,043,840 bytes — 5.7x the frame**. Downstream the damage is silent and total: ffmpeg's rawvideo input is offset for good, so the *first* picture decodes perfectly and every one after it is drawn rolled, with no error from ffmpeg, from the sink, or from the encoder wrapper. One `write()` then `await flush()` is the whole correct form (`writeFrameToSink` in `android-video.ts`). Two things generalise. A frame **counter** cannot see this — every counter in the pipeline reported the right number while 5.7x the bytes left the process — so the test has to measure the bytes a real child receives (`tests/unit/android/android-video-frame-write.test.ts`), and it needs a chunk big enough that the sink buffers in pieces or the bug does not reproduce at all. And a capture that decodes correctly proves nothing if it holds one access unit: the first frame is always right.
- **`dateStyle`/`timeStyle` may not be combined with any other `Intl` option**: `toLocaleString(undefined, { dateStyle: "medium", timeStyle: "medium", timeZoneName: "short" })` does not ignore the third option, it *throws* `TypeError: dateStyle and timeStyle may not be used with other DateTimeFormat options`. Behind the `try/catch` that any date formatting picks up sooner or later, that is indistinguishable from a locale which simply has no timezone in its medium format — the commit details panel showed author and committer dates with no zone at all, and no test caught it because the fallback string is perfectly well-formed. A format that needs a companion option has to list every component explicitly (`year`/`month`/`day`/`hour`/`minute`/`second` + `timeZoneName`), and the test worth writing runs the options object through a real `Intl.DateTimeFormat` and asserts the *output* contains a zone.
- **A project folder is often not the repository, and every git surface has to agree on which one is**: a workspace folder can be a container whose children are the checkouts, and `simple-git` in a directory with no `.git` does not report "wrong directory" — it fails with git's own wording, which the UI renders as "not a git repository" for every panel at once. The scope is one `?repo=` parameter resolved in a middleware in `src/server/routes/git.ts` and one hook, `src/web/hooks/use-git-repo.ts`, on the browser side; `GET /git/repos` is the discovery. Four things are load-bearing. The parameter is **omitted** when the repository *is* the project root, so every URL an ordinary project builds stays byte-identical and the common case cannot regress on this path. A `repo=` outside the project must be a **400, never a fallback** to the project folder — a fallback runs the command one directory up and answers with *a* history, which is indistinguishable from a working feature until somebody acts on it. Paths cross in **both** directions: git run inside the repository reports and expects repository-relative paths while a tab's `filePath` is project-relative, so `rebaseStatusPaths` moves the *tree decorations* into the project's terms and the panel's own copy stays as git reported it, because that copy is what stage/unstage/discard/hunks send straight back. And `useGitRepo`'s return value is `useMemo`d: call sites name `gitRepo` in a dependency array, so a fresh object literal per render turns one `useCallback` into an effect that refetches forever. Watch the panel's own early returns too — `fetchStatus` deliberately does nothing until a repository is resolved, so a spinner gated only on `loading && !status` waits for a fetch that will never run and the chooser never renders.
- **A white screen has two causes and only one of them is catchable**: both start with a hashed chunk the browser asks for and the server does not have — `vite build` runs with `emptyOutDir`, so an upgrade deletes every previous hash while a tab is still naming them. `static.ts` used to SPA-fall-back on *any* missing path, so that request came back as **`200 text/html`**, which a module load refuses on its strict MIME check; `static-fallback.ts` now decides by `Sec-Fetch-Dest` (plus `/assets/` and `/monacoeditorwork/` as the prefix, because browsers omit Fetch Metadata on an insecure origin and PPM is usually reached over plain HTTP on a LAN). The path's *shape* cannot be the test: PPM's routes embed file paths, so `/project/x/editor/src/main.js` is a navigation whose extension is `.js`. Then: a **lazy** chunk failing throws inside `React.lazy`, and a throw past the last boundary unmounts the entire tree — `main.tsx` had no root boundary, so `#root` simply emptied. But the entry's own graph is **39 separately-hashed chunks** (rolldown names one of them `settings-tab-*` while the entry statically imports it, so the name says nothing), and one of those missing means the entry module *never executes*: no React, no boundary, no listener, nothing bundled to report it. That is what the inline watchdog in `index.html` is for, gated on the `__ppmEntryRan` flag `main.tsx` sets so the two can never both fire. The service worker made either one **permanent**: `CacheFirst` on `/assets/` had stored that `text/html` under the chunk's URL and content-hashed assets are never revalidated, so restoring the file on the server fixed nothing and only `caches.delete("ppm-assets")` did — hence the plugin refusing to store *or* serve HTML on both runtime caches, `cleanupOutdatedCaches()`, and the `skipWaiting`/`clients.claim()` that `registerType: "autoUpdate"` never actually implemented in `injectManifest` mode. Two things will hide the bug while you try to reproduce it: `Cache-Control: immutable` means a chunk already in the HTTP cache is served from disk however hard the server 404s, and `CacheFirst` means one already in `ppm-assets` is too — a cold origin (a different port) is the only reliable reproduction.
- **`Bun.spawn` throws on a missing binary rather than reporting it, and every per-OS tool is a missing binary somewhere**: it raises `Executable not found in $PATH` *synchronously*, so a `try` placed around the awaited output — the natural reading order — never sees it and the exception escapes a function typed `Promise<RunResult>`. `src/services/host-info/spawn-runner.ts` is shared by the `systemctl`, `plutil`, `powershell.exe`, `findmnt` and `xdg-user-dir` providers, i.e. by five tools that are each absent on two of the three platforms, and there the throw turned the Services page on macOS and Windows into a 500 showing the exception — past a collector that answers `supported: false` and a panel that has a branch for exactly that. A missing binary is returned as a *failed run* (`code: null`, message on stderr) because that is the shape callers already branch on; `gpu-collector-nvidia.ts` had been carrying its own `try` around the same hazard all along, which is the tell that it was known and not generalised. Two things to take from it. Reproduce a platform you do not have by removing what it lacks — `env PATH=/nonexistent bun -e '…'` took the Services collector from `THREW` to `supported: false` in one command, and no amount of reading the file would have. And the narrowed spawn type has to be preserved when the call moves into a `try`: `ReturnType<typeof Bun.spawn>` widens `stdout` back to a union with a raw fd that `new Response()` rejects, so name a helper and take `ReturnType<typeof helper>`.
- **On macOS `/tmp` and `/var` are symlinks into `/private`, so a path guard comparing one spelling protects nothing there**: every fs door checks a path and its real path, and a real path never spells a root through a symlink — so a PPM directory under `/tmp` (every test's `PPM_HOME`) matched only the first check, and a symlink to `ppm.db` was served as an ordinary file. `fs-credential-path-guard.ts` compares each protected root (PPM dir, `~/.cloudflared`, backups) by its configured **and** its real spelling, resolved once per root. An exception is never spelled by its *own* real path: the uploads and codex-image exceptions are the PPM dir's spellings plus their subpath, and they lift only the PPM-dir refusal. Resolving `uploads` itself — the first version of this fix — let a link put in its place carry the exception to the link's target: the snapshot directory, or the PPM dir and `ppm.db` with it. The `fs-sqlite` route test had been failing on every Mac for exactly this reason, which read as a flaky test.
- **Hono's global `cors()` overwrites the `Access-Control-Allow-Origin` a route sets**: headers set before the handler are copied over the handler's response, so `design-preview.ts` re-asserts `null` in a middleware after `next()`, and its unit test mounts `cors()` like the real server. The same re-wrap (`new Response(res.body, res)`) makes Bun lose a `BunFile.slice()` body: behind `cors()` a `rangeFileResponse` 206 for `bytes=2-5` sends `Content-Length: 8` and bytes 2 to EOF. That one is still open; route unit tests mount without `cors()`, which is why none caught it.
- **The dev bundle's terminal connects straight to `:8081`, whatever server the page came from**: `use-terminal.ts` bypasses Vite's WebSocket proxy in dev, so under the html-preview harness (random API port) every terminal sits on "Reconnecting…" — and if a dev PPM is up on 8081, an e2e's terminal opens a shell *in that instance* and types into it. Check `ss -ltn` for 8081 first; to test a live terminal, put the scratch API on 8081 itself. React's `StrictMode` also double-mounts it in dev, so each terminal spawns two shells and a handed-over command is typed into both, showing twice in one xterm — dev only; a production build mounts once.
- **The pre-migration database snapshot is skipped whenever `CURRENT_SCHEMA_VERSION` lags the migrations**: `backupBeforeMigrations` returns early for a database already at that version, and the constant sat at 47 while migrations reached 49, so a database at 47 ran 48 and 49 with no snapshot. Bump it with every migration; `db-session-design-slug.test.ts` asserts a migrated database ends at it.
- **A PreToolUse hook verdict needs `hookSpecificOutput.hookEventName: "PreToolUse"`**: the bundled CLI reads `permissionDecision` only when the event name matches ("Hook returned incorrect event name" otherwise), so without it a Deny the user clicked did not block the tool. `preToolUseDecision()` in `claude-agent-sdk-query-options.ts` builds every verdict.
- **`resolveSessionDir` falls back to scanning every Claude project on disk**: given a session id whose encoded project path does not resolve, it walks every `~/.claude/projects/*` looking for a matching `<sessionId>.jsonl` — useful for a session started outside PPM, unsafe if trusted before the caller is known to own that session. `src/services/agent-transcript/session-ownership.ts` is the gate every Agent-session transcript read goes through first instead; the `/ws/global` hub never accepts a client-supplied path for this reason.
- **`Bun.spawn({ stdin: other.stdout })` is not a pipe between two children**: Bun reads every byte into PPM and writes it back out with a pump of its own (measured: piping 200 MB raised the Bun process's own `rchar` and `wchar` by 200 MB each). Two failures follow, both silent until the reader dies. Under a burst, that pump rejects with `EPIPE`s nothing can catch — 2–3 per remux death with keyframe-sized writes, and `handleFatalError` in `src/server/index.ts` exits the server at 3 in a minute. And a reader that stalls before dying leaves the writer running for good, because Bun is still reading it: gst-launch kept encoding with no `onExit` and the viewer sat on a frozen picture. `remote-desktop-capture-wayland.ts` therefore pumps gst into the remux itself (one awaited `write()` + `flush()` per chunk, the same shape as the `FileSink` entry above) and watches **both** processes, the first to die taking the other down. `wayland-capture-supervision.test.ts` drives it with shell stand-ins; under `bun test` an unhandled rejection is a failed test, which is what makes the burst case assertable at all.
- **The error that ends a turn is in no transcript, so anything rebuilt from history drops it**: a Max Turns stop reaches the browser as an `error` event and a `done` with `resultSubtype: "error_max_turns"`, and Claude's JSONL ends at the turn's last tool result. A reload rebuilds the chat from that transcript, and so does the end of any turn long enough to overflow the 10,000-event reconnect buffer (thinking deltas fill it), where `replayTruncatedRef` refetches history at idle — so the one red line saying why the session stopped vanished, and the notification said "Chat completed". `turn-stop-reader.ts` reads how the last top-level turn ended back from the session trace (a cancel, a newer message or a turn still running means no stop; rows with `parentToolUseId` are a subagent's), `session_state.turnStop` carries it to every greeting, `turn_stop` goes out just before the `done`, and `useChat` keeps it apart from `messages` so a refetch cannot erase it. Several `session_state` builders (model, effort, thinking) omit the field, which is why the client only touches `turnStop` when the key is present. Verify with `node tests/e2e/turn-stop-e2e.mjs` (`PPM_PLAYWRIGHT_MODULE` if Playwright is not installed here).
- **`PRAGMA auto_vacuum` takes the write lock even when it changes nothing, so `busy_timeout` must be set first**: the session trace set it after `auto_vacuum`/`journal_mode` (copied from `query-audit-db.ts`, which still has that order), and a second process opening the file while another was mid-write got `SQLITE_BUSY` at once — measured: a lock held for 300 ms failed the open outright against a 2 s timeout. Only the full unit suite's server-plus-CLI race caught it. `journal_mode = WAL` on a file already in WAL does *not* wait on a writer, which is why `db.service.ts`'s order is harmless. Put `busy_timeout` first in any opener two processes share.
- **A terminal with no layout is fitted to 2x1, and zsh does not survive 2x1**: xterm's FitAddon never proposes less than 2 columns by 1 row, which is exactly its answer for a 0x0 container. A terminal is mounted with no layout more often than it looks. The dock's active tab is mounted while the dock is hidden (`collectFromDock` marks it active either way), and a phone restores every dock collapsed (`collapseRestoredDockOnMobile`). Fitted at mount, such a terminal got 2x1, and its socket sent that size on open. zsh with a themed prompt then corrupted its own heap redrawing at 2 columns. glibc aborted it with `double free or corruption (!prev)` on the first keystroke after the terminal was shown, up to an hour later and at an ordinary size. That is why every core in `coredumpctl` read 156-269 columns and none pointed at a resize. Replayed against zsh with an oh-my-zsh + oh-my-posh config: left at 2x1 or 2x2, 20 of 20 shells died on that keystroke; at 3x1, 10x1, 2x20, 156x1 or 80x24, none did, and a bare zsh survived 2x1. Every `fit()` in `use-terminal.ts` now asks `proposeDimensions()` first, and `terminalService.resize` drops anything `isUsableTerminalSize` (20x2, `src/shared/terminal-size.ts`) rejects, so a browser on an older bundle cannot do it either. Two lessons for the next one. A crash that lands long after its cause needs the history of the shell's size, and the live PTYs hold it: `stty -F /dev/pts/N size` on each `zsh` under `ppm.service` found a hidden terminal still sitting at 2x1. And the ResizeObserver's own `contentRect` zero check was never enough, because its debounced fit runs 100 ms later, when the tab may already be parked. Verify with `PPM_E2E_DIST=<scratch dist> node tests/e2e/terminal-hidden-resize-e2e.mjs`, which reads the size from the shell's tty rather than from xterm.
- **A bounded read of a file stream has to count its own bytes and end with `cancel()`**: on Bun 1.3.11, `Bun.file(f).slice(a, b).stream()` never finishes when `b` is well short of the end of a multi-MB file — the last `read()` neither resolves nor errors (a 4MB file's `slice(0, 259)` hung; `slice(0, size - 1)` and an endless `slice(a)` did not) — so `readLines` takes `toByte` and stops at it itself. And a reader let go of before its end with `releaseLock()` keeps its file descriptor: 2000 early stops left 2000 open, `reader.cancel()` closes it. Both bite the windowed transcript reads in `compact-segment.ts`, which stop early on every scroll up by design; `compact-segment.test.ts` pins both.
- **Rebuilding a table that others reference deletes their rows unless foreign keys are off — and that pragma is ignored inside a transaction**: SQLite's recipe for changing a constraint (create the new table, copy, drop the old one, rename) is how migration 55 let `connections` accept `mysql` / `mariadb`. With `foreign_keys = ON`, `DROP TABLE connections` runs an implicit `DELETE` that cascades through `connection_table_cache`'s `ON DELETE CASCADE` and empties it before the new table exists — no error, just a cache that is gone. `PRAGMA foreign_keys = OFF` is a no-op inside a transaction, so `allowConnectionTypes` in `db.service.ts` turns it off *before* `BEGIN`, reads it back and refuses to run when a caller's transaction kept it on, and restores it afterwards. It also rebuilds from the table's own recorded SQL with only the CHECK replaced, so a column a later migration added is carried over, and keeps the `AUTOINCREMENT` high-water mark, because query-audit rows still name the ids of deleted connections.
- **History pairs a tool's result with its call inside one message, so results must be merged into the message that holds the call**: the Claude SDK writes every content block as its own record, so two calls made at once are two assistant records followed by both results. The old merge put every result on the *last* assistant message, which left the first call's card with no result — fine while streaming, then lost when the chat refetches history at the end of the turn. `mergeToolResultMessages` in `jsonl-transcript-parser.ts` routes each result by `toolUseId`, and both history paths (`getMessages` and `parseJsonlTranscript`) use it.

## Architecture

Each subsystem's own map sits with its gotchas in that directory's `CLAUDE.md`.

- `src/providers/claude-agent-sdk.ts` — SDK integration, tool execution, streaming
- `src/server/ws/chat.ts` — WebSocket chat handler
- `src/web/hooks/use-chat.ts` — Frontend chat state management
- `src/services/config.service.ts` — Config from SQLite (`~/.ppm/ppm.db`)
- `src/web/components/floating-window/` — Desktop window manager (drag/resize/z-band/persistence), OS-agnostic
- `src/web/components/os-explorer/` — OS File Explorer window body: views (List/Icons/Column), skins, mobile sheet, actions, drag-and-drop
- `src/services/fs-ops/` — Guarded whole-disk filesystem operations (`/api/fs/*`) behind PPM auth
- `src/services/host-info/` — Per-OS drives/known-folders/pinned-folders providers (`/api/system/host`)
- An application is not a process: `app-rows.ts` folds processes into apps by the systemd app cgroup they live in (`app-<desktop-id>[-<pid>].scope`, `app-<id>@<hash>.service`), and `/api/system/app-icon/:id` serves that app's own desktop-entry icon. That route is the one place the `?token=` query fallback in `middleware/auth.ts` was widened to — an `<img>` cannot send an `Authorization` header — and it is only safe because it takes an **app id, never a path**. Keep it that way.
- `src/services/db-backup/` — verified `VACUUM INTO` snapshots of `ppm.db` (hourly + at start + before every migration), GFS retention, `ppm backup` / `ppm restore`
- `src/services/git-hunks/` — hunk/line-level stage, unstage and discard (`/api/projects/:name/git/{hunks,stage-hunks,unstage-hunks,discard-hunks}`). `unified-diff.ts` holds the patch surgery (recomputed `@@` counts, unselected deletions demoted to context); the UI is `src/web/components/git/hunk-stage-dialog.tsx`
- `src/services/git-repos/` — which repository a project's git surfaces run in, when the project folder is a container of checkouts rather than a repository itself. `git-repo-discovery.ts` walks the folder (`GET /git/repos`), the `?repo=` middleware in `src/server/routes/git.ts` scopes every git route to one of them, and the browser side is `src/web/lib/git-repo-scope.ts` (pure decisions and both directions of path rebasing), `src/web/stores/git-repo-store.ts` (the device-local choice), `src/web/hooks/use-git-repo.ts` (what every panel calls) and `src/web/components/git/git-repo-picker.tsx`. Extension panels are opened on the repository, so `packages/ext-git-graph/src/project-scope.ts` maps that path back to the containing project
- `src/services/git-changes/` + `src/services/git-workflow/` + `src/services/git-discard-journal/` + `src/services/git-commit-draft.service.ts` — Source Control, the Review changes tab and the Git Graph as one flow over the same routes. `GET /git/changes` is the working tree file by file and block by block (one `git status --porcelain=v2`, at most one `git diff` per side, `GIT_OPTIONAL_LOCKS=0`; a block's id is the fingerprint `git-hunks` resolves), every POST on the git router emits `git:changed` on `/ws/global`, a discard is kept for Undo under `<ppm dir>/git-discards/`, and the commit message is one per repository in `chat_drafts` (`git:commit-draft`). UI: `src/web/components/git/git-status-panel.tsx` and its `git-*.tsx` parts (decisions in `src/web/lib/git-changes-view.ts`), the `git-review` tab in `src/web/components/git-review/` over `src/web/lib/git-review-model.ts`, and the Git Graph reaching the same routes through `packages/ext-git-graph/src/ppm-git.ts` — a git write that bypasses them is heard by nobody until the next poll. The Git Graph's file icons are the app's, answered per name by `src/web/components/extensions/webview-file-icons.ts`. Docs `docs/architecture/workspace-and-ui.md` → Source Control, Review changes and Git Graph
- `src/server/routes/static-fallback.ts` + `src/web/components/root-error-boundary.tsx` + `src/web/lib/chunk-recovery.ts` + the inline watchdog in `src/web/index.html` — the four halves of not going blank when a chunk is missing: 404 instead of the shell, a boundary above `App`, one guarded purge-and-reload on `vite:preloadError`, and a dependency-free last resort for when the entry never ran at all
- `src/services/git-blame/` — `git blame --porcelain` for the editor's inline annotation (`/api/projects/:name/git/blame`); shared shape and formatting in `src/shared/blame.ts`, editor wiring in `src/web/hooks/use-inline-blame.ts`. The annotation's GitLens-style hover adds one `git show --unified=0` per commit *and line* (`/git/commit-line`, parsed by `commit-line-diff.ts`), with the markdown built in `src/web/lib/blame-hover.ts` and its buttons registered in `blame-hover-commands.ts`, which hand off to the Git Graph extension's own views over `ext:command:execute`
- `dist/web` asset pipeline — `scripts/copy-monaco.ts` stages `monaco-editor/min/vs` under `dist/web/assets/monaco/` (inside `assets/` so it inherits the immutable cache header, the SW runtime cache and the compressed siblings), `scripts/precompress-web.ts` writes `.br`/`.gz` siblings, and `src/server/routes/static-encoding.ts` chooses one per request (honouring `q=0` and `*`, keeping the original MIME, adding `Vary: Accept-Encoding` and the encoding in the ETag). Both scripts run after `build:web` in the `build` chain
- `src/services/named-tunnel/` — Named tunnel (stable `https://<prefix>.<zone>` URL via Cloudflare login), orchestrated from `src/server/routes/named-tunnel.ts`, spawned/probed by the supervisor; UI in `src/web/components/tunnels/named-tunnel/` (the setup flow, shared by the first-run popup and Settings)
- `src/services/notification.service.ts` — notifications, configured in Settings → Notifications. `broadcast(type, payload, { stillUnseen })` drops a switched-off event, waits `delay_seconds` (one pending per session: a newer event replaces it) and sends only if `stillUnseen()` still holds — the chat is still unread, and for an approval the same request is still pending (`src/server/ws/chat.ts`); schedules and Jira pass none and always send. `deliver` fans out to push, Telegram and ntfy, plus PPM Cloud's `sendNotification`, which is inert in the server process because that connection lives in the supervisor. Settings shape and defaults in `src/shared/notification-settings.ts`, text and links in `notification-format.ts`. Push is standard Web Push with no dependency, `src/services/web-push/` (VAPID ES256 + RFC 8291 aes128gcm on WebCrypto; keys and subscriptions are the config rows `web_push_vapid` / `web_push_subscriptions` and never reach a browser); the browser half is `src/web/sw.ts` (`push`, and `notificationclick` → `src/web/sw-notification-click.ts`, which hands the session to an open window through `src/web/hooks/use-notification-clicks.ts`) and `src/web/lib/web-push-{support,client}.ts`. Telegram sends through `telegram-notification.service.ts` to the chats in the `telegram_notify_chats` config row, and to nobody else: PPMBot has a bot and chats of its own (`telegram-bots.ts` — the `ppmbot_telegram` row and `clawbot_paired_chats`; both rows sit outside `CONFIG_TABLE_KEYS` like the VAPID key, and an install that shared one bot is split once, on first read). The one-tap Connect link is `telegram-connect.service.ts`, one per bot owner, which polls a bot itself unless PPMBot is reading that bot (Telegram allows one `getUpdates` reader per bot; the bots are compared by id, the digits before the token's colon). ntfy is `ntfy-notification.service.ts`: one JSON publish per notification (the header form cannot carry a non-ASCII title), the config row `ntfy` with its token in `SECRET_CONFIG_KEYS`, dropped when Settings saves a different server so it is not sent to the new one (`PUT /ntfy`; `ppm config set ntfy.server` does not drop it). Both channels take their link back into PPM from `notification-link.ts`: the tunnel URL, else the Tailscale Service address, else localhost — never the LAN address, which is plain HTTP on an insecure origin where the browser withholds every permission PPM asks for. Routes `src/server/routes/notifications.ts` (`/api/notifications/*`), UI `src/web/components/settings/notifications-settings-section.tsx` + `telegram-bot-token-field.tsx` + `ntfy-server-form.tsx`, fake ntfy for tests `tests/helpers/fake-ntfy-server.ts`
